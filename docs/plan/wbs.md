## 2 触发源与调度

维护期一半的问题不会自己敲门,但**发现它们不是平台要做的事**:Caddy 会报证书过期,云雀会报容量,扫描器会报 CVE。平台只做一件事——把这些系统的投递接进来,变成同一种信号。入口已经只剩一个(`POST /webhook/{source}`,按适配器声明的 `source` 分发),所以接一个新系统 = 一个声明 `produces: signal` 的适配器,核心一行不改。

**当前范围**:默认只启用 GitHub 的 issue 与 PR,统一成 `kind = issue / comment / merge` 三种事件。CNB 适配器已补齐议题 / 评论事件、`comment.create`、`pr.open` 与 `workspace_source`,但仍是预留位(`default_enabled: false`);GitLab 只做合并触发,告警适配器形状已定。要用时打开清单里的开关或加进 `PLUGINS_ENABLED`。

三件"假设只有一个来源"的事已经收口:取代码、回评、评论触发词都按投递自身的 `source_adapter` 解析,核心没有默认来源。

调度器是另一回事:它只服务"只会被问、不会主动说"的来源(某些扫描结果只有 API、没有 webhook),以及 §3 的到点收口。

## 5.5 工作区

补回了项目这一级(`projects.parent_id` 为空的那一行),议题板有了三档范围闸。

[工作区模型](../explanation/workspace-model.md)与[身份与授权](../explanation/identity-and-authorization.md)。
剩下的是真正让它成为 SaaS 的那一件:同一份身份多个工作区共用,形状与迁移四步见

## 怎么用这张表

1. 开工前读[平台架构](../explanation/platform-architecture.md)与[变更单元契约](../explanation/change-unit-contract.md),确认这件事有没有被决定过。
2. 新的设计先写进 `explanation/`,再进这张表。实现按文档走,不按记忆走:文档没写的决定,等于还没有做。
3. 挑依赖已满足的行,把状态改成 `进行中`。
4. 验收判据跑通了才删行;删行时不写"已完成",历史在 git。
5. 新工作先查表内是否已有条目:有就改对应行,不另开清单。


## 建议顺序

1. **1.1**。一条门控用例,把账本的结论钉死;后面所有判定都建在它上面。
2. **2.1**。调度器只在"对方不会主动说"时才需要(拉取型来源),排在链路被证明之后。
3. **2.3** 按决定推迟:适配器形状与样板已在,接哪个系统等有真实目标再定。
4. 其余按依赖推:4 与 5 可以并行,6 只在对外经营时才需要。
