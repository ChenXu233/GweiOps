# 身份模型:人是全局的,角色是工作区给的

> 状态:决定中 | 日期:2026-11-16 | 读者:后端、前端、维护者
> 上游:[工作区模型](workspace-model.md)、[运行时参考](../reference/runtime.md)

这份文档回答一件事:**一个人在多个工作区里到底是什么**。它决定 `users` 表还能不能当"人",决定令牌与请求之外的第二个维度(工作区)怎么进判定,也决定成员页和邀请的入口长什么样。

**§1–§5 是我按现有约束推出来的方案,§6 是要维护者拍板的七个决定。** 拍板前不动 `users` 表结构 —— 那里存的是登录凭据,行拆错了代价只在修复,不在迁移。

## 1 一句话

**一次凭据指向多道门;一次请求只进一道门。**

## 2 今天的形状与它必然坏在哪

`users` 一行同时装着两件不同生命周期的事:

| 一行里的东西 | 属于谁 |
| --- | --- |
| `email`、`password_hash`、`last_login_at` | **这个人**。跨工作区是同一件东西 |
| `tenant_id`、`parent_id`、`permissions`、`UserRole` | **这个人在这一个工作区里的**角色与从属关系 |

只要一个人只属于一个工作区,合在一行没有代价。他凭邀请进第二个工作区时,按 `uq_users_tenant_email` 必须再插一行:同一个邮箱的第二份密码、两个"最后登录时间"、两把令牌,改密码要改两处 —— 然后两处必然漂移。这不是"以后再说"的问题,是**邀请功能一上线就会发生**的那类问题。

角色表(`roles.permissions`)本来就按租户分开,`UserRole` 是把"人"接到"某个租户的角色"上的那条边。所以**按工作区给角色的能力已经存在**,缺的是"这个人"这一侧有地方放。

## 3 目标形状

```text
person ──credential──▶ 能登录的凭据(email / password / 联系方式)
   │
   └──membership──▶ 工作区(租户) ──role──▶ 权限
                       └──repo grant──▶ 某个仓库上的权限
```

三条判据:

1. **凭据唯一**:一个邮箱在整个部署里最多一份 `password_hash`。改密码只改一处。
2. **角色随工作区**:同一个邮箱在 Acme 是 owner、在 Beta 是 viewer。角色不跟人走。
3. **空集不是默认**:登录成功不等于能看账。没有成员关系的人拿到的是一个空权限身份,请求结果是 403 且说得出原因,不是"看到第一个工作区"。

### 3.1 表和代码的对应

| 今天 | 变成 | 谁在读 |
| --- | --- | --- |
| `users`(凭据 + 一个工作区 + 角色) | `person`:`email` / `password_hash` / `last_login_at` / `display_name`。`email` 全局唯一 | 登录、改密码、找回密码 |
| `users.tenant_id` / `users.parent_id` / `users.permissions` | `membership`:`person_id` / `tenant_id` / `parent_membership_id` / `permissions` / `status`。`(person_id, tenant_id)` 唯一 | 权限判定、成员页、子用户 |
| `user_roles(user_id, role_id)` | `membership_roles(membership_id, role_id)`。`roles` 不变,仍是每个租户一套 | 权限判定 |
| `user_sessions.user_id` | `user_sessions.person_id`:**一次登录,多道门** | 会话解析 |
| `user_contacts.user_id` | `person_id` | 核验、找回 |

**权限判定本身一行不用改。** `effective_permissions(own, roles, parent, parent_scoped)` 的入参今天是"这个人的个人追加权限 + 他在这一个租户的角色 + 父用户那一侧",换成成员关系后取到的仍是这三样。变的只是**取之前先确定"哪个工作区"**。

### 3.2 一次请求怎么选工作区

现在 `tenant_scope()` 从令牌里读租户:"令牌说哪个就是哪个,请求参数不一致就 403"。会话 cookie 是人的凭据,它不该把租户写死在里面。

```
请求 ──▶ 凭据是谁(会话 / 密钥 / 静态令牌)
      ──▶ 这一步落在哪个工作区
      ──▶ 在那个工作区算出有效权限
```

选工作区的顺序,三个来源一个优先级:

| 来源 | 谁用 | 与别的来源冲突时 |
| --- | --- | --- |
| `X-Gwei-Workspace` 请求头 | 控制台(工作区选择器写它) | —— |
| 库里 `users.last_workspace`(上次用的那个) | 控制台没带头时 | 它只是建议,不是边界 |
| 令牌声明的租户 | 机器(`X-Gwei-Token`) | **静态令牌与密钥仍是"写死一个租户",今天的 403 行为不变** |

两条规则写在这里,不靠界面提醒:

- **请求头点名的那个工作区,这个人必须是成员**。不是成员就是 403(或按"看不到这个工作区"处理),不是悄悄落回他有权限的那个 —— 静默降级会让人以为自己在看 Acme 的账,实际是 Beta 的。
- **一次请求只在一个工作区里算权限**。不做"把几个工作区的权限并起来",那是越权的起点。

这两条和 `tenant_scope()` 今天的态度是同一个:**不一致就报错,不覆盖。**

### 3.3 权限判定与范围

工作区选完,判定回到已有的两层:

| 层 | 写法 | 落地情况 |
| --- | --- | --- |
| 工作区级 | `changes.approve` | 已有 |
| 仓库级 | `changes.approve@github-acme-api` | 已有(PR ChenXu233/gweiops#26) |
| 项目级 | 未定 | **不做**,见 §6.3 |

项目这一级今天只是分组(见[工作区模型](workspace-model.md))。再往上加一个"项目级授权"要回答"仓库级的值从哪读、回显谁看得见、推给插件时按哪个仓库推",这是一圈不小的机制。**角色在项目上暂时不加**,靠仓库级授权覆盖真实需求(要管一个项目下的所有仓库,就逐个仓库授权)。

### 3.4 子用户与邀请

- **子用户**是"同一个工作区内的从属关系",所以 `parent_membership_id` 指成员关系,不是人。一个人在 Acme 是某个人的子用户,在 Beta 可以是 owner —— 这条正是拆开之后才说得清的。
- **邀请**是"把一个人接进一个工作区"。今天没有这个功能(见[工作分解](../plan/wbs.md) 6.5),它需要的正是这张成员关系表:邀请里存的是工作区与被邀请的邮箱,对方接受时要么认领一个已存在的 person(邮箱相等),要么新建一个。

**认领这一步是安全边界,不是便利:** 邮箱相等才认领,并且要求对方能证明控制这个邮箱(核验码 / 邀请链接里的一次性令牌)。没有证明就认领等于把别人的账号送人。

## 4 迁移与兼容

迁移只做一次,但分两步落,因为中间那一步不能有停机窗口:

| 步骤 | 做什么 | 判据 |
| --- | --- | --- |
| a | 建 `person` / `membership` / `membership_roles`,把今天的 `users` 行按 `(tenant_id, email)` 一对一填进去 | 每个旧 `users.id` 都能在 `membership` 里找到且只找到一条 |
| b | 审计:同一个 `email` 出现在两个租户里时,列出这些组,由人决定合并还是保留 | 一份清单,不是自动合并 —— 自动合并要猜"哪个密码是真的" |
| c | 读切到新表。`users` 保留为视图或保留到下一次版本,写路径已不在 | 登录、会话、成员页、审计全走新表 |
| d | 删 `users` 的旧列 | 迁移是一条链,down 有损:合并过的人拆不回去 |

`a`–`d` 都在一条迁移链上,和 [012](../..) / [013](../..) 同一条。**在决定 1 之前不动手**,因为"合并还是保留"决定了 b 步是自动还是人工。

### 4.1 令牌与密钥不受影响

`X-Gwei-Token` 的格式 `token:tenant:actor:scope` 与库里的密钥都是"机器凭据",它们本来就写死一个租户。身份拆开之后它们仍然是租户边界的一部分:密钥属于某个工作区,签发它的人改了工作区不影响它。

所以**身份重构不动机器那一侧的任何判定**,只动"人"。这是这次改动面看起来大、实际小的原因。

## 6 要维护者拍板

每条都写清楚:**选项是什么、各自代价、我选哪个、为什么、选错了能不能改。**

### 决定 1:拆表,还是每个工作区一行用户?

| | A. 拆(person + membership) | B. 不拆,一个邮箱每个工作区各一行 `users` |
| --- | --- | --- |
| 密码 | 一份,改一处 | 每个工作区一份,**必然漂移** |
| "这个人" | 有主体,能跨工作区看"我在哪几家" | 没有主体,`GET /api/me` 只能说"这是这个工作区里的某个 id" |
| 邀请 | 认领已有 person 或新建 | 每次都要新建一行、设第二个密码 |
| 改动面 | 迁移 + 登录/会话/成员/审计的读路径 | 零 |
| 选错能不能改 | 拆了合不回去(密码要人工裁决),但拆的方向是单向正确的 | 随时能补拆,只是越晚越贵(漂移的密码读不回来) |

**我选 A。** 理由不是"更优雅",是 B 下"改密码"这件事没有一个正确答案:哪个工作区的密码才是这个人的?界面上无论怎么答,另一个工作区的自己就登不进去了。这不是能用一个提示绕过去的问题。

**B 唯一的实际优势是零改动。** 如果你认为短期内不会有"一个人属于两个工作区"(比如每个工作区都是独立的付费客户,不会有人被邀进第二家),B 是合理的 —— 那就把 5.5.1 降级、只留 5.5.1a 之外的部分,等真出现再拆。**这一条请你明确说"做 A"或"先不做"。**

### 决定 2:登录凭据的边界 —— 密码在部署级还是工作区级?

A 之下还有一层要选:

| | A1. 密码是部署级的(一个人一份,登录后选工作区) | A2. 密码是工作区级的(登录时带工作区,各工作区一份) |
| --- | --- | --- |
| 心智模型 | 跟 GitHub 一致:登录 GitHub,再切 org | 跟"每个客户一套独立系统"一致 |
| 拆表收益 | 拿满:一份凭据、一次登录、多道门 | 基本没了:还是要两份密码,只是能从一处改 |
| 一个已知的风险 | **企业客户可能不接受"你的员工用同一个密码登录我们和别家"** | 客户之间完全隔离 |

**我选 A1。** 理由是 A2 会保留 B 的全部代价,只省掉"两处改密码"这一项 —— 收益抵不上多出来的一层"这个工作区用哪份密码"的判定。

**但 A1 有一个真实的商业风险,必须由你判断:** 如果 GweiOps 要卖给别人,而"别的工作区"是另一家公司,那么"同一个人"这件事本身就不该跨客户存在 —— 那时正确的答案不是 A1 也不是 A2,而是**部署级不共享**:客户之间根本不在同一个库里。这条走不走,决定 5.5.1 值不值得做。

**请回答的是:A1 / A2 / 还是"客户之间不共享部署,一人多工作区只发生在同一家公司内部"?** 第三种情况下我给 A1,但把"认领 person"限制在同一个部署内,并且要求邮箱核验(见 §3.4)。

### 决定 3:工作区的选择走请求头,还是走路径?

| | A. 请求头 `X-Gwei-Workspace` | B. 路径 `/api/workspaces/{slug}/...` |
| --- | --- | --- |
| 现有接口 | 一个都不改:所有 `/api/*` 保持原路径 | **每个**接口路径都多一段,前端每个调用点都要改 |
| 分享链接 | 只有路径,工作区在浏览器状态里 —— 发给同事会落到同事的当前工作区 | 链接自带工作区,发出去就是同一道账 |
| 聊天/邮件里的深链 | 同上 | 天然正确 |
| 缓存/CDN | 按路径缓存的规则要改(同一个 URL 两种内容) | 无影响 |
| 静态令牌 | `token:tenant:...` 本来就写死租户,与请求头不冲突 | 同样不冲突 |

**我选 A。** 理由:B 的收益(链接自带工作区)能用 `/issues?ws=acme` 这种查询串拿到,不必让每个接口路径都多一段;而代价(每个调用点都改)是实打实的。

**选 A 要接受一件事:** 浏览器标签页停在 Acme、同事打开同一个链接会看到他的当前工作区。如果你认为"链接必须表达完整上下文"是硬要求,那选 B,现在改比以后便宜。

### 决定 4:成员关系的 id 要不要暴露成 `user_id`?

成员页今天按 `user_id` 操作(改角色、停用、设密码)。拆表后有两种入口形状:

| | A. 接口保留 `user_id`,值是**成员关系的 id** | B. 接口改成 `person_id` + 工作区 |
| --- | --- | --- |
| 前端改动 | 只改字段含义,不改调用形状 | 每个成员操作都要多带工作区 |
| 语义准确 | 需要文档说一句"这个 id 是你在当前工作区的身份" | 字面上就准 |
| 跨工作区操作 | 不成立:一个人在两个工作区的 `user_id` 不同 | 天然成立(`person_id` 一个) |

**我选 A。** B 会引出"用 `person_id` 在 Acme 里改 Beta 的角色"这种既合法又没人想要的操作,而 A 里跨工作区的管理通过 `/api/workspaces/{slug}/members` 表达 —— 工作区在路径上而不是在 id 里。

这条是**内部形状**,选错了改起来便宜(前端字段改名),不急。

### 决定 5:项目级授权做不做?

| | A. 不做(角色只到工作区 + 仓库) | B. 做(角色可以授在项目上) |
| --- | --- | --- |
| 能表达的 | "这个人管 acme/api 和 acme/web" | "这个人管 acme 这个项目下的所有仓库(含以后新增的)" |
| 机制 | 已有 | 要回答"回显谁看得见、推给插件推哪个仓库、新增仓库自动获得吗" |
| 规模 | 0 | M–L,且是逐 scope 的一圈机制 |

**我选 A,并且建议长期不加。** "以后新增的仓库自动获得"听起来是 B 的优点,实际是它最难的一块:项目下新加一个仓库,是自动把授权扩过去(那么"授权"就有了时间维度),还是不加(那么 B 和 A 只差一次批量的 A 操作)?两种答案都成立,但没有第三种。批量授权一个按钮就够了。

**请回答"A / B"**;选 B 我要先写"新增仓库是否自动获得授权"这条规则,再动手。

### 决定 6:`users` 表怎么退场?

| | A. 两步:先加新表双写,确认后删旧列 | B. 一步:迁移里搬完直接删 |
| --- | --- | --- |
| 风险 | 低;中间态能回滚 | 迁移失败要回滚整个版本 |
| 耗时 | 两个版本 | 一个版本 |
| 现在能不能做 | **能**:库里用户数与工作区数都还小,一次性搬完是安全的 | 能 |

**我选 B(一步),理由是现在数据量小,双写带来的代码复杂度不值得。** 但这条有个前提:**这个部署已经在给别人用了,就不能选 B** —— 那时双写是唯一安全的。

**请回答:现在是"还没给别人用"(可以一步)/ "有人在用"(必须两步)。**

### 决定 7(顺手要一句):`?repo=` 与 `?project=` 那两个查询串的自定范围变量,要不要一起换成工作区头?

这条可以放到 5.5.1a 里一起做,可以不做。**不回答我就按"一起做"走**:同一个东西(当前在哪个工作区)在请求头里已经说了一次,查询串里再说一次就是第二个真相源。
