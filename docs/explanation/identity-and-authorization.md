# 身份与授权:人是全局的,角色是工作区给的,授权沿资源链继承

> 状态:现行 | 日期:2026-11-17 | 读者:后端、前端、维护者
> 上游:[目标](goals.md)的「形态」、[工作区模型](workspace-model.md)
> 下游:[运行时参考 · 鉴权](../reference/runtime.md)

这份文档回答三个问题:**谁在调用**、**他在哪能做什么**、**一个插件被允许自动做什么**。前两个是身份,第三个是授权;两者共用同一条资源链,所以写在一页里。

## 1 一句话

**一次凭据指向多道门;一次请求只进一道门;授权沿 工作区 → 项目 → 仓库 继承。**

## 2 四条地基

| # | 判断 | 推出的东西 |
| --- | --- | --- |
| 1 | 平台不拥有身份,只绑定身份 | "你是谁"由上游回答(OIDC / GitHub / CNB 账号,selfhost 下是本地管理员),平台只认结果 |
| 2 | 授权是主干,不是附属 | 边界必须和 GitHub / CNB 同形:主体 × 资源 × 动作,资源是 工作区 / 项目 / 仓库 |
| 3 | 插件是主体,不只是配置项 | 它从接入、诊断、执行到报告贯穿全流程,"这个插件被允许在哪些仓库上自动做什么"就是一条授权 |
| 4 | 工作区走路径 | `/api/workspaces/{slug}/...`:资源就得有 URL,链接自带工作区 |

第 3 条是[目标](goals.md)「形态」那节的落地:授权清晰的地方自动做,授权不到或不可逆的地方才等人。**授权是半成品,平台就不知道一个插件被允许在哪自动做什么,"全流程自动化"立不起来。**

## 3 资源链

```text
用户 ──成员角色──▶ 工作区(租户) ──项目──▶ 仓库 ──议题 / 变更账本 / 事故 / 执行会话
```

| 层 | 落在哪 | 授权长在哪 |
| --- | --- | --- |
| 用户 | 部署级一份凭据 | 无 |
| 工作区 | `tenants` | 工作区级角色(owner / operator / viewer) |
| 项目 | `projects` 里 `parent_id` 为空的行 | 项目级授权,覆盖它下面每一个仓库 |
| 仓库 | `projects` 里指向项目的行 | 仓库级授权 |

**工作区就是租户,项目与仓库共用 `projects` 一张表**,理由见[工作区模型](workspace-model.md):同一个边界两个名字,只会引出没人答得上来的问题。

## 4 授权的形状

权限是原子字符串,收窄时写 `权限@范围`,范围是 `projects` 里的 slug:

```text
changes.approve                      整个工作区都能放行
changes.approve@acme                 整个 acme 项目(含以后新增的仓库)
changes.approve@github-acme-api      只在这一个仓库上能放行
```

判定链是 **repo → project → 工作区**,判据只此一处(`engine/api/auth.py` 的 `require`,以及 `Identity.allows` / `Actor.allows`):

| 判据 | 为什么 |
| --- | --- |
| 项目与仓库共用一个名字空间 | 两者都在 (租户, slug) 上唯一,所以 `acme` 与 `github-acme-api` 天然区分,不需要第二套语法 |
| 项目授权覆盖**以后新增的**仓库 | 所以这一档不能在建身份时展开成一份仓库清单,只能判定时问——展开的那一份,在新仓库进来时没有人回来改 |
| 只有读账 / 执行 / 放行 / 撤销能收窄(`SCOPED_PERMISSIONS`) | 它们最终都落在一个仓库上。管人、管密钥、改配置是工作区级的事,写成 `users.manage@…` 直接丢掉 |
| 带范围的授权不算工作区级权限 | 不点名范围的判定 403,而且说的是"这个权限只对具体范围生效",不是"缺少权限" |
| 子用户与父按范围逐个取交集 | 父只管 `acme/api`,子用户借角色把自己铺到 `acme/web` 不算数 |

**为什么做项目这一档,而不是"批量勾一次仓库就够了"。** 用第一性原理想:管道跑的是一个项目——一个项目下多个仓库,同一套发布策略、同一批插件目标。授权只能落到仓库时,项目下每加一个仓库都要重勾一遍,**自动化的流程里嵌了一步手动操作**。项目档把这一步去掉,这正是"决策不一样"要的那部分。

## 5 人是全局的,角色是工作区给的

凭据属于**这个人**,角色属于**他在这一个工作区里**。这两件事生命周期完全不同:改密码是一次性的、跨工作区的;换角色是每个工作区各管各的。装在同一行里,同一个人进第二个工作区就必须再插一行:第二份密码、两个"最后登录"、改密码要改两处,然后两处必然漂移。

形状:

```text
person ──credential──▶ 能登录的凭据(email / password / 联系方式)
   │
   └──membership──▶ 工作区(租户) ──role──▶ 权限
                       └──scope grant──▶ 某个项目或仓库上的权限
```

| 判据 | 落地 |
| --- | --- |
| 凭据唯一 | 一个邮箱在整个部署里最多一份 `password_hash`(`persons.email` 唯一),改密码只改一处 |
| 角色随工作区 | 同一个邮箱在 Acme 是 owner、在 Beta 是 viewer,角色不跟人走(`memberships` 一行一套) |
| 空集不是默认 | 登录成功不等于能看账;没有成员关系的人拿到空权限身份,403 且说得出原因 |
| 工作区在路径里 | `/api/workspaces/{slug}/…`;不属于它就是 403 并点名,不替他落回他有权限的那一个 |
| 一次请求只在一个工作区里算权限 | 不把几个工作区的权限并起来,那是越权的起点 |

### 5.1 表

| 表 | 一行是什么 | 关键判据 |
| --- | --- | --- |
| `persons` | 一个人 | `email` 在整个部署里唯一;`password_hash` / `last_login_at` 只在这里 |
| `memberships` | 一个人在**一个工作区**里的身份 | 主键 `user_id`,唯一键 `(tenant_id, person_id)`;`parent_id` 指父成员,`permissions` 是这个工作区给的个人追加 |
| `user_sessions` | 一次登录 | 挂 `person_id`:换工作区不重新登录 |
| `user_roles` | 成员 × 角色 | `user_id` 是成员关系的;角色本来就属于一个租户,两者同一层 |
| `user_contacts` / `password_reset_tokens` / `external_identities` | 联系方式 / 找回密码 / OIDC 绑定 | 都挂 `person_id`:这些跟着人走,换工作区不该重验一遍 |

`user_id` 这个列名保留了下来,值是**成员关系的 id**。会话、审计、`user_roles`、"谁点的头"问的一直是"这个工作区里的哪个人",不是"这台机器上的哪个人"。改成 `person_id` 会引出"用同一个 id 在 Acme 里改 Beta 的角色"这种合法又没人要的操作。

**权限判定本身一行不用改。** `effective_permissions()` 的入参仍是"个人追加 + 他在这个租户的角色 + 父成员那一侧",变的只是取之前先定"哪个工作区"。

### 5.1a 请求怎么选工作区

```text
GET /api/workspaces/acme/changes      ← 路径里的那一段说了算
GET /api/changes                      ← 没说,按令牌 / 会话自己声明的那个
```

判据只此一处(`engine/api/auth.py` 的 `workspace_access`):

| 情形 | 结果 |
| --- | --- |
| 路径里写了,且他是那个工作区的成员 | 用这个 |
| 路径里写了,但他不是成员 | 403,说清是哪个工作区 |
| 路径里没写,令牌 / 会话声明了工作区 | 用令牌那一个 |
| 路径里没写,令牌的租户是 `*` | `None` = 不限(跨租户的维护令牌) |
| 路径里没写,也没有人登录(没配鉴权的部署) | `None` = 不限 |

**空串与 `None` 不是一回事**:`None` 是"不限",空串是"一个工作区都没有"。把不限写成空串,账本会按空租户去筛,一行都读不出来 —— 那是把权限放大成看不见,同样是个 bug。

查询串的 `tenant` 不再生效:两份真相源迟早一边说 Acme 一边说 Beta。折路径与定工作区在中间件里是**同一步**(`make_middleware`):只折不定,请求会落到默认工作区;只定不折,路由认不出。

### 5.1b 迁移与审计

迁移 `018_person_membership` 一次到位:`users` 的每一行按 `lower(email)` 并成一个 person,同一个邮箱的多行取最早那一行做 person,成员关系逐行搬。一次到位的前提是**这个部署里还没有第二个工作区的人**;有的话先跑下面的清单再迁。

`scripts/identity_audit.py` 列出"同一个邮箱挂在两个以上工作区"的那几组,结论写在 `deploy/identity-merge.json`,每条只能是:

| 结论 | 含义 | 后果 |
| --- | --- | --- |
| `merged` | 同一个人 | 一条 person,两条成员关系 —— 迁移就是这么做的 |
| `kept` | 不是同一个人(或暂时说不清) | 各留一条 person,邮箱必须已经改掉一个:两条同邮箱放不进去 |

判据:**每一组都有结论**,同一个库跑两遍输出一样。写错的结论当场拒绝,不当成"没写" —— 那会让"做完了"变成一个谎。

机器那一侧不动:`X-Gwei-Token` 与库里的密钥本来就写死一个租户,拆表之后它们仍是租户边界的一部分。**身份重构只动"人"**,这是改动面看起来大、实际小的原因。

### 5.1c 邀请:邀请里不存密码

"把人拉进来"有两条路,分工只有一句话:**谁定密码**。

| 谁定密码 | 怎么走 | 什么时候用 |
| --- | --- | --- |
| 管理员替他定一个临时密码,带外告诉他 | `POST /api/users` | 联调、临时账号 |
| 他自己定 | 邀请:发一条链接,他点开、设密码、成为这个工作区的人 | 正常开通流程 |

邀请这一行只装**工作区**与**被邀请的邮箱**。密码不进来 —— 那是被邀请人自己的事,也是"同一个人进第二个工作区不该有第二份密码"这条的落地。

| 判据 | 落地 |
| --- | --- |
| 令牌只存哈希 | `invitations.token_hash`,和会话令牌一样:库被看到也换不出能用的链接 |
| 只能用一次 | 接过之后 `accepted_at` 留着,再点得到"这条邀请已经用过了",不是一个 404 |
| 过期说清下一步 | `expired` / `used` / `revoked` 三种状态各回一句能照着办的话 |
| 同一个邮箱只留一条没接的 | 再发一条,前一条当场作废 —— 同时有效的邀请越多,撞上来的机会越多 |
| 已经在这个工作区里的人不发 | 发了他也接不了,给两边都添一件事 |
| 角色在发的时候定死 | 接的人没有改动余地;要额外给什么,是管理员在成员页上再改一次的事 |
| 接的时候认**邮箱** | 部署里已经有这个人 → 认领:只加一条成员关系,他的密码一个字都不动;没有 → 他现场设一次密码 |

`GET /api/invitations/{token}` 与 `POST /api/invitations/{token}` **不要登录**:被邀请的人那时还没有账号,不该为了接一条邀请先有权限。这条豁免只覆盖那一个 token 路径(`engine/api/auth.py` 的 `INVITE_PATH`),列表与发邀请仍然要 `users.read` / `users.manage`。

接完顺手发一个会话给他 —— 少一步登录。

### 5.1d 成员这一栏也能带范围

范围授权(`changes.approve@acme`)原来只能挂在角色上。一个工作区里"张三能放行项目 acme、李四能放行仓库 acme/api"这种分工,靠角色表达只能建一堆只差一格的角色。

所以成员行自己的 `permissions` 里也允许写带范围的条目,判定走同一个 `split_scoped`。上限仍是自己那一条,判据是"我手上的这个权限覆盖不覆盖这一步":

| 我手上 | 能给出去的 |
| --- | --- |
| `changes.approve`(工作区级) | 整个工作区的放行权,以及任何范围的放行权 |
| 只有 `changes.approve@github-acme-api` | 只能给这一个仓库,给不出 `acme`(项目档),更给不出整个工作区 |

收窄了的权限不在 `SCOPED_PERMISSIONS` 里的(`users.manage@acme`)写入时直接丢掉,不猜 —— 猜成工作区级会多给。

## 6 插件作为主体

插件拿到的授权范围,就是它能自动化的边界。它与人走同一条链:主体 × 资源 × 动作,资源仍是 工作区 / 项目 / 仓库,动作由它声明的能力给出。

| 插件能拿到什么 | 判据 |
| --- | --- |
| 一个 scope(工作区 / 项目 / 仓库) | 授权清晰 = 在这个范围内可撤可验的地方自动做;`autonomous_capabilities` 是预授权名单,空 = 一律等人 |
| 一个 binding | 单元带 binding,提供者声明 binding;不一致时拒绝执行,不降级 |
| 一组效果(execute / undo / window / verify) | 没有 `undo` 的效果只能出现在人在回路的路径 |

**插件与人的授权不并成一张表。** 人问的是"谁能进这个仓库",插件问的是"它被允许在哪些仓库上自动做什么";两者粒度不同,混在一张表里迟早有一边被扭曲。同一张表表达的是同一条资源链,不是同一类主体。

## 7 已有接口

| 接口 | 用途 |
| --- | --- |
| `GET /api/permissions` | 权限目录,前端据此画勾选框 |
| `GET /api/workspaces` | **我进得去**的工作区,以及每个里面有几个仓库、来自哪些平台 |
| `GET /api/workspaces/{slug}/repos` | 这个工作区里的仓库,每行带来源、slug 与所属项目 |
| `GET /api/workspaces/{slug}/projects` | 这个工作区里的项目,以及每个项目下面有几个仓库、几条议题 |
| `GET /api/me` | 我是谁、属于哪些工作区、每个里面是什么角色 |
| `GET /api/invitations` / `POST /api/invitations` | 这个工作区发出的邀请,以及发一条新的(响应里的令牌只出现一次) |
| `DELETE /api/invitations/{id}` | 撤销一条还没接的邀请 |
| `GET /api/invitations/{token}` / `POST /api/invitations/{token}` | 看一条邀请现在什么情况 / 接它。不需要登录:链接里那枚令牌就是凭据 |

工作区不在的路径(`/api/repos`)照样能用:它按令牌 / 会话自己声明的那个工作区回答。机器那侧(静态令牌、密钥、`/mcp`)只有这种形状 —— 它们的租户本来就写死。
