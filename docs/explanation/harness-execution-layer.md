# Harness 执行层

> 状态:现行 | 读者:架构 / 后端
> 上游:[变更单元契约](change-unit-contract.md)、[插件系统参考](../reference/plugin-system.md)
> 口径:本文讲"agent 在哪跑"这件事的边界。配置项与线上口径见[运行时参考](../reference/runtime.md) § Harness。

## 1. 位置

harness 不是新的一层,是 **intent 的提供者**:一个普通 agent 插件,把信号变成单元里的意图和候选效果。用哪个 agent 运行时(dsh / WorkBuddy / 自研 / CNB 的 NPC)由清单或镜像声明。

分工:变更单元定义「改什么、怎么撤、算不算成」,harness 定义「谁想出这个改动」,沙箱定义「它在哪台机器上下笔」。

## 2. 一次运行只有五件事

平台要的从来不是"连上一台机器"或者"挂上一个目录",而是这五件:

| # | 动作 | 为什么单独一步 |
| --- | --- | --- |
| 1 | `prepare` 把本次运行的目录树送进去 | 代码、任务书、凭据都是字节;怎么落进去取决于目标环境是什么 |
| 2 | `handshake` 认一下它还在不在 | 云开发环境要先孵化才有地址,别的地方拉起就有 |
| 3 | `invoke` 跑一条命令,等它结束 | 长命令不能占着一次握手的寿命 |
| 4 | `fetch` 把产物取回来 | 取产物不该要求会话还活着 |
| 5 | `entries` 说清它跑在哪 | 人在回评里看到的是一个编号和一条能点开的地址 |

接口就是这五个动作(`engine/harness/sandbox.py`)。**换一个地方跑 = 换一个提供者**,
`run_harness`、出口、账本、可撤销承诺一行不改。

会话的生命周期归提供者管,平台只问"这一刻它还活着吗"。这不是抽象洁癖:CNB 的
云原生开发环境从发出到能连上要几十秒,期间的失败重试、地址刷新都是它自己的事。

## 3. 三条通道,同一份契约

| 提供者 | 边界 | 交进去 | 带回来 | 适合 |
| --- | --- | --- | --- | --- |
| `local` | 本机进程 | 直接写工作区 | 直接读工作区 | 单机部署;隔离靠命令自己 |
| `ssh` | 一个常开的会话 | `scp` 一份代码包 | `scp` 取报告与改动 | 云原生开发环境、手边的跳板机 |
| `cnb` | CNB 托管执行面 | 整包挂在 `env` 里交进去 | 只取改动包 | cnb.cool 上默认的边界 |

### 3.1 为什么默认是 `cnb` 而不是云原生开发环境

CNB 的云原生开发环境(`POST /{repo}/-/workspace/start`)确实是最"隔离"的形态,但
它的取用方式是 `get-workspace-detail` 返回的一串 `ssh user@host`,没有凭据就一步也
走不了;每次运行还要重新孵一次环境。这种取用方式已经由 `ssh` 提供者备好了 —— 需要它的时候
把地址与私钥配上就行。

`api_trigger` 构建没有这些问题:令牌就是凭据;配置随请求交上去(`config` 字段),
不用往仓库里写 `.cnb.yml`;退出码、日志、构建号都从 API 拿得到。所以 cnb.cool 上的
默认边界是它。

### 3.2 代码怎么来回

远端沙箱没有平台的文件系统,所以走"一串字节",分三件事:

1. **进去**:平台把本次运行的目录树压成 `workspace.tar.gz`,`base64` 后挂在 `env` 里。
   CNB 会把 `env` 里的 `$NAME` 渲染成真值,这是唯一一条能交任意长度内容的通道。
   交进去的内容超过 `MAX_INLINE_BYTES` 就不硬塞:要么配上 `object_storage`
   走"平台签一个地址、沙箱按地址 PUT",要么先解决仓库规模问题。
2. **就地**:CNB 自己检出的仓库在 `/workspace`,构建脚本把它摊进平台的工作区
   (`--skip-old-files`,已存在的以平台交进去的为准)。
3. **回来**:平台取回**改动过的文件**,在本地对着基线算出"改了哪些、多少行"。

第 3 条是执行层最要紧的一条:**改了什么由平台数,不由沙箱自报。** 让沙箱自己数,
平台就只能信一句话,而那句话既核不了、也回滚不了。代价是平台要能把改动拿回来 ——
所以改动包是回程通道的必要组成部分,不是优化。

## 4. Worker 边界

- Worker 不写业务库,不持有 Issue / PR 状态;控制面持有全部业务真相;
- 每次模型调用归属到租户,超配额由网关拒绝;
- 沙箱里没有生产凭据。它要改生产,只能调出口——契约第 7 节第 6 条。

## 5. 部署

- 每租户一个沙箱配置;托管版的模型调用走网关的 per-tenant key;
- 自托管同一份 compose,租户数 N=1;
- 换机器不改命令:`SANDBOX` 换个值就够。

## 6. 待定

- `object_storage` 的签名地址由谁签(平台自己的对象桶 / CNB 的制品库)?
- 远端沙箱里的代码要不要缓存到下一次运行(省一次整包搬运,但多一份会过期的副本)?
- 报告与改动的保留期:构建记录在 CNB 那边有寿命,平台这边要不要留一份?
