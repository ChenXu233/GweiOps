# 议题工作台

> 状态:设计待审 | 日期:2026-11-14 | 读者:前端、后端
> 上游:[目标](goals.md)、[变更单元契约](change-unit-contract.md)

界面只服务一件事:**把议题处理掉**。其余的东西——变更账本、执行记录、事故报告——都是这件事的证据,不是并列的工作对象。

但"简化"不等于"少给信息"。处理议题的人要能一路下钻到命令输出,还要能接着上一轮让 agent 改下去。**默认简化,按需展开**是这份设计的基本约束。

## 1 一句话

**一个议题,一条时间线,两个动作;信息分两层,改动分多轮。**

## 2 心智模型

原来有十一个导航项、五个概念(议题 / 待放行 / 变更 / 事故 / 执行),用户得先学会它们的区别才能干活。现在侧边是三组八项,概念收在议题下面。实际上用户只关心三件事:

1. 有什么**在等我**;
2. 系统**正在做什么**;
3. 昨天的改动**做成没有、能不能撤**。

它们都是同一个对象在不同阶段的说法。界面上原来有三个与议题重叠的入口——控制室、待放行、执行记录——现在都没有了,它们问的问题分别落在:

- **今天要我做什么** → 议题板的「等我」段;
- **系统正在做什么** → 议题板的「在跑」段,与详情里的轮次;
- **昨天的改动做成没有** → 议题板的「落了」段,与详情里的结论。

## 3 三个状态

数据库里的状态有五六个,变更的结论有七种。**列表上只看到三个**:

| 用户看到的 | 含义 | 从哪些证据来 |
| --- | --- | --- |
| **等我** | 有人必须做点什么,不做就不动 | 变更的 `blocked` / `unknown`;事故开着没收口(可能卡住);一条变更都没有、而议题还开着 |
| **在跑** | 没人要等,系统在执行或在看 | 变更的 `pending`;执行会话还没结束 |
| **落了** | 有结论了,不再需要人 | 变更的 `kept` / `rolled_back` / `irreversible` / `vetoed` / `failed`;一条变更都没有而议题已关闭 |

判定在 `engine/change_unit/timeline.py` 的 `normalize_state` 里,**列表与详情共用它**。

七种结论**原词不出现在列表上**:`kept` 写成"已改好,还能撤 12 分钟",`irreversible` 写成"改好了,但撤不回来了"。原词留给账本页。

## 4 页面

### 4.1 议题列表(默认首页 `/`)

三段,从上到下:

1. **等我**:标题、来源、等你做什么(放行 / 否决 / 去核 / 继续改)、停留了多久。
2. **在跑**:标题、现在第几轮、做到哪一步。
3. **落了**:按时间倒序,每条一行——标题、结论一句话、能不能撤。

顶部只放三个数字与一个筛选框,不再放"系统态势"那种大色块——它不是用户要做的决定。

### 4.2 议题详情(`/issues/:id`)

- **头部**:标题、来源与仓库、**当前分支与 PR**、一句话结论,以及此刻可做的动作。
- **主体**:时间线(见 §5)+ 迭代(见 §6)。
- **右栏**:涉及的服务与仓库、涉及的变更单元(链接到账本行)、原始记录入口。

### 4.3 两层信息:默认摘要,按需展开

**概要层**(默认展开):每一步一句人话。
**证据层**(点开):对应步骤的完整输入输出——意图 JSON、变更参数、验证查询与结果、命令输出、下游返回码。

规则:

- 摘要层**不允许省略信息类别**:一句人话下面必须能点到原文,不能只给结论不给依据。
- 证据层**不做二次加工**:存了什么显示什么,截断要标明截断。
- 摘要与证据共用同一条时间线,不另开"详情页的详情页"。

### 4.4 工程决策要点

处理议题的人要判断"这个改法对不对",所以每个变更单元必须能回答四个问题:

| 要点 | 从哪来 |
| --- | --- |
| **打算做什么、为什么** | `intent.summary` + `intent.rationale` + `intent.evidence` |
| **为什么是这个做法** | 被放弃的候选与放弃理由(模型给的备选、策略挡下的动作) |
| **动了什么、影响面** | 变更单元的 `effect`(能力 + 参数)、触及的文件 / 服务 / 目标 `binding` |
| **怎么撤、撤不了怎么办** | `undo` 的形态、窗口读到的结果、验证查询与阈值 |

四个要点**始终在时间线里**,不折叠成一句"已生成方案"。方案细节属于工程决策,不属于可省略的噪声。

## 5 时间线:全流程

从上到下按发生顺序,一段对应一件事:

```text
信号    哪里出了什么事(来源、主体、原文)
诊断    看到了什么(日志、代码、指标)
意图    打算做什么、为什么、依据
变更    动了哪个目标、什么参数、怎么撤
验证    查了什么、阈值是多少、结果
结论    保留 / 回滚 / 阻断 / 不知道
```

每段两种形态:概要一句 + 展开原文。"结论"里如果带了不可逆,要写明是**哪一步**让它不可逆(没有句柄 / 读不到窗口 / 撤销失败),不是一句"不可逆"。

## 6 迭代:一条分支上的多轮

一个议题往往不是一次改完的。人看了 diff 说"这里该用 X",agent 要**在原分支上接着改**,而不是重新开一个 PR。

### 6.1 引擎已经有了什么

- 话题就是 `owner/repo#n`;同一话题上已有打开的 PR 时,新改动接着该 PR 的分支走([变更单元契约](change-unit-contract.md) 第 9 节);
- harness 的任务书里已经写明接着原分支改,`pr.open` 的 head 用该分支([adapter.py](../../engine/harness/adapter.py));
- **从界面发起**:`POST /api/issues/{id}/continue` 把人的一句话排成一轮
  `fix_suggestion_workflow`,与 `@gwei` 评论是同一条路——分支沿用、PR 不新开是
  `fix_suggestion_workflow` 的既有行为,不是另写的一套判断。人说的话进 signal,事故把它记下来,
  所以它就是时间线上的一个新轮次。

### 6.2 界面上是什么样

- 详情页有一个**轮次列表**:第 1 轮、第 2 轮……每轮显示"人说了什么 → agent 改了什么(文件与行数)→ 验证结果"。
- 每轮的改动可以看 diff,按文件分组;跨轮可以只看向上取整的合并 diff。
- 底部常驻一个输入框:**继续改**。提交后开一轮新的执行,沿用同一个话题与分支,结果追加到列表。
- 没有分支时(还没开 PR)输入框照样在,第一轮会开分支;后续轮次复用它。

### 6.3 规则

- **轮次不覆盖**:上一轮的 diff 与结论保留,新一轮追加。
- **每轮一个事故**:失败可以单独回看,不会被下一轮的成功掩盖。
- **继续改不是"再试一次"**:它是人的新指令,写进账本的 `intent` 里,谁让改的、改什么,可查。

## 7 导航

三组八项。与议题重叠的三个入口(**控制室、待放行、执行记录**)连页面一起删了:
它们问的都是"要我做什么 / 做了什么",答案在议题板(等我 / 在跑 / 落了)与详情的时间线里。
留着没有入口的页面,半年后没人说得清它还算不算数。

```text
工作区   议题(默认)   变更账本
接入     仓库   信号源   插件
系统     指标观测   成员   设置
```

侧边徽标只保留一个:**等我**的条数。

## 8 动作规则

| 动作 | 什么时候出现 | 之后 |
| --- | --- | --- |
| 放行 | 该议题有 `blocked` 的变更 | 照常读窗口、照常验证,不过就回滚 |
| 否决 | 同上 | 记为 `vetoed`,不再执行 |
| 回滚 | 有已执行、且撤销仍有效的变更 | 追加一行审计;窗口过期则不可用并说明原因 |
| 去下游核 | 有 `unknown` 的变更 | 只给出口,不假装能一键解决 |
| 继续改 | 任何时候(输入框常驻) | 开新一轮,沿用同一话题与分支 |

按钮不常驻:没有可做的动作时,动作区显示"现在不需要你做什么",不留灰按钮——**输入框除外**。

## 9 时间线的边界

时间线只有一个来源:`GET /api/issues/{id}/timeline`。聚合在
[timeline.py](../../engine/change_unit/timeline.py) 里做,接口只取数;三个状态、
轮次、分段都在同一个响应里。前端的职责是渲染,不是拼装。

| 段 | 从哪来 |
| --- | --- |
| 信号 | 事故的 `signal_source` / `signal_title`;没有事故时用这次执行的来源(issue / comment / merge) |
| 诊断 | `AgentSession.state.analysis` |
| 意图 | 单元的 `intent`:summary / rationale / evidence / effects(候选动作)/ skipped(没做的候选与理由) |
| 变更 | 单元的 `effect`(能力、参数、撤销方式、声明里的验证规则)与 `binding` |
| 验证 | `effect.verify` 里的 `{query, expect}` + `facts`(下游返回的结构化事实),过没过由结论反推 |
| 结论 | 单元的 `verdict` / `reason` / `window` / `handle` |

**线上的空缺不是排版问题,是没记。**只剩一处边界:

- **补丁本体**是一个边界,不是欠账:轮次上有"改了哪几个文件、各多少行",没有"这
  个文件的哪几行变成了什么"——要看行级内容就点进 PR。行级补丁留在代码托管那边,
  平台不复制一份会过期的副本。

一轮里一个候选都没落成单元时,理由也不会丢:工作流把整份意图(含
`skipped`)交回,事故记着它,时间线据此说出"本打算做什么、为什么都没做"。

验证查了什么、候选为什么没做,这两处**已经补上**:插件的声明里本来就有
`verify: [{query, expect}]`,现在随单元一起落账(事后读它不依赖插件还在不在);
被放弃的候选与理由由工作流在建单元**之前**写进 `intent.skipped`——有没有提供者、
有没有被扩展点拦下,只有建单元之前才知道。
