# SaaS 交付形态:共享默认、专属可选

> 状态:现行 | 日期:2026-11-17
> 读者:维护者。取舍来自 Issue #24 中「你懂什么叫 SaaS 吗」那一轮;本文只写结论与判据。

## 1 一句话

**共享部署是默认,专属实例是同一份代码的另一种摆法。**

「客户之间不共享部署」曾经写在工作分解 §5.5 的待定项里。那条是错的:它把**交付形态**
写成了**架构约束**。工作区(租户)这道边界从第一天起就在队列分区、账本、密钥、成员、
配置 scope 里;一人多工作区、路径化工作区、按范围授权那一整套,只有在共享部署里才有
意义 —— 否则每个客户一套,「多工作区」就只剩同一家公司内部互相邀请这一种用法。

| 形态 | 谁跑 | 隔离靠 | 何时用 |
| --- | --- | --- | --- |
| 共享 SaaS(默认) | 我们跑一个部署,按工作区隔离 | 行级安全 + 租户边界 | 自助注册进来的客户 |
| 专属实例(企业版) | 同一份代码,一份专属部署 | 网络与数据库隔离 | 合规、私有网络、要自己的域名与审计 |

两栏是**同一份代码、同一套迁移、同一条租户边界**,差别只在物理摆放。这正是
`deployment_mode` 已经定下的形状([平台架构](platform-architecture.md) §2):
`saas` 档启用登录/注册/工作区/计费;`selfhost` 档是单租户 N=1 且不装计费插件的
同一份代码。**selfhost 是「客户自己想跑一份」的选项,不是「我们不敢开共享」的默认。**

## 2 共享部署要成立,三件事是硬要求

下面三条不是选项,是共享部署的准入条件:任何一条做不到,整盘不成立。

### 2.1 隔离落在库上,不落在每条 SQL 上

应用层过滤的强度是「漏一处就串数据」;行级安全的强度是「漏一处就报错」。共享部署
里数据的价值决定了必须是后者。

**「哪些表必须受策略约束」只有一份清单**:`engine/db/tenancy.py` 的
`isolated_tables()`(今天 28 张表)。迁移 `020` 照它建策略,`.ci/engine-tests.py`
照它对一遍模型(带 `tenant` / `tenant_id` 列却没登记的表会让 CI 红),启动时
`ensure_isolation()` 再对着库查一遍,`deployment_mode=saas` 缺一张就**拒绝启动**。

清单必须在代码里,不能是文档,也不能是库里的一行:新加一张表是写代码那一刻的事,
写进文档或写进库都要有人记得同时补一处 —— 那正是「新表没有策略」的成因。

策略表达式一律是「**连接明确声明不限,或者这一行的租户等于连接的工作区**」:

```sql
current_setting('gwei.tenant', true) = '*'
  OR tenant_id::text = current_setting('gwei.tenant', true)
```

| 判据 | 为什么 |
| --- | --- |
| 缺省是「一个工作区都不属于」 | 会话变量为空 → 比较恒假 → 看不见任何行。默认拒绝,不是默认放行 |
| 「不限」写成 `*`,不是空串 | 空串在策略里是「所有租户之外的那个值」,结果是静默的 0 行,而不是都看见 |
| 核心自己的连接也写租户 | 不写的话核心一条数据都读不出来;而「为了读得出来就不写」等于把隔离让给每一处 SQL 的自觉 |
| 跨工作区的读要显式声明 | 认证(`resolve_key`)、维护脚本、清表走 `connecting("*")` / `connecting_any()`。名字长一点是故意的:读代码的人该看见它 |

派生表(`patches` / `pull_requests` / `approval_votes` / `agent_sessions` /
`audit_log`)没有自己的租户列,租户口径由父表推;`persons` 一行跨工作区只有一份,
它的策略问的不是「属于谁」而是「谁能看见」(自己那一行,或本单位有成员关系的)。

受限角色 `gwei_plugin_reader` 仍然只走三张 `security_invoker` 视图,它拿到的连接
缺省也带着空的租户。

### 2.2 一个工作区能在十分钟内自己接完,不改库不找人

判据:一个陌生人拿到部署地址,自己走完注册 → 建工作区 → 接第一个来源 → 第一条工作流
跑通,全程不碰数据库、不找人要凭据。走不完时,每一步都要说清缺什么。

**注册即建工作区**(§6.7):没配 `registration_tenant` 时,`create_user` 按邮箱给
他建一个工作区(`newbie@example.com` → `newbie`),连同三个预设角色;他在里面是
`registration_signup_role`(缺省 owner)。配了 `registration_tenant` 时仍落进那一个
—— 那是单租户自部署的形状,给新来的人另建一个工作区反而把他隔在外面。

**开通状态**(§6.2):`GET /api/workspaces/{slug}/onboarding` 回答四步(工作区 /
接入来源 / 接进仓库 / 跑通第一条工作流),每步带 `done` 与 `next`,`next` 是**人能
照办的那一步**(「打开「信号源」页填令牌;缺的是 `GITLAB_WEBHOOK_TOKEN`」),不是
一句「未完成」。它只读:状态从来源配置、仓库数、议题与账本现算,不落一张「开通进度」
表 —— 那种表迟早与事实对不上。

「接进仓库」这一步是**人做的显式动作**(§5.5.5):仓库页选来源、填全名接入,来源清单
由装着的适配器答。投递只喂已接入的仓库 —— 没接入就来投递,返回 `unconnected` 并说清
去哪接。开通的判据因此是"人接过一个仓库",不是"某条投递碰巧落进过这个工作区"。

### 2.3 用量能变成钱,而且对得上账

计费单位没定(§6.3)。共享部署里这一条不落地,产品就只是「免费额度」。
判据:给定一个月的数据,账单条目能逐条对上账本与 LLM 计量;对不上的行要能列出来。

## 3 选专属实例时,共享那一半不白做

专属实例**不换代码**,所以共享 SaaS 里做的隔离、开通、计量它全部继承。区别只有三处:

| 关注点 | 共享 | 专属 |
| --- | --- | --- |
| 工作区个数 | 任意 | 通常一个(把整个部署当自家组织) |
| 注册 | 自助,对外开放 | 通常关掉,由管理员建 |
| 计费插件 | 装 | 按合同装或不装 |

所以「先只卖专属实例」在技术上等价于「`deployment_mode=selfhost` + 手工建租户」,
不需要为它删掉任何东西;但**共享 SaaS 里那些工作必须做完,专属实例才卖得出去**——
一套连客户之间都隔离不干净的代码,装进客户的机房同样不安全。

## 4 和插件的关系

插件是**主体**,不是配置项([目标](goals.md) §形态)。共享部署里这层意思更硬:
同一个插件实例要同时服务多个客户,那么「它被允许在哪几个工作区、哪些仓库上自动做什么」
必须在每次调用时判定,不能靠部署隔离兜底。

- 每一次进出插件的调用都带着租户;插件读库走 `plugin_session`,事务里 `SET LOCAL` 租户
- 插件的能力解析按 (租户, 目标),选不到直接抛,不跨租户回退

插件的数据可见范围是这条链:三张 `security_invoker` 视图(按查询者求值)→ 基表策略
(按连接上的 `gwei.tenant` 收口)→ 受限角色只有 `SELECT`。三环缺一环都等于把可见范围
交回给「插件自己的 SQL 写对没写对」。视图与受限角色由迁移 `014` 建、`020` 重新钉过一遍
权限(那里的 `REVOKE … ON ALL TABLES` 会顺手带走视图的读权限)。

## 5 结论

| 判断 | 依据 |
| --- | --- |
| 共享部署是默认形态 | SaaS 的定义就是「一个部署卖多家」;租户边界已经在代码里 |
| 专属实例是同一份代码的另一种摆法 | `deployment_mode` 已定:saas / selfhost 唯一代码路径 |
| 隔离必须做到库级 | 共享部署下应用层过滤的失效率不可接受 |
| 自助开通比计费更靠前 | 没有自助开通就不存在 SaaS 这个产品,只是我们替客户开库 |
| 隔离要能被检查,不能靠记 | 策略靠人记,就等于没有策略:清单在代码里,CI 对模型,启动对库 |
| 插件在共享部署里必须按调用判租户 | 一个插件实例同时服务多个客户 |
