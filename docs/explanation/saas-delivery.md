# SaaS 交付形态:共享默认、专属可选

> 状态:现行 | 日期:2026-11-17
> 读者:维护者。取舍来自 Issue #24 中「你懂什么叫 SaaS 吗」那一轮;本文只写结论与判据。

## 1 一句话

**共享部署是默认,专属实例是同一份代码的另一种摆法。**

「客户之间不共享部署」曾经写在工作分解 §5.5 的待定项里。那条是错的:它把**交付形态**
写成了**架构约束**。工作区(租户)这道边界从第一天起就在队列分区、账本、密钥、成员、
配置 scope 里;一人多工作区、路径化工作区、按范围授权那一整套,只有在共享部署里才有
意义 —— 否则每个客户一套,「多工作区」就只剩同一家公司内部互相邀请这一种用法。

| 形态 | 谁跑 | 隔离靠 | 何时用 |
| --- | --- | --- | --- |
| 共享 SaaS(默认) | 我们跑一个部署,按工作区隔离 | 行级安全 + 租户边界 | 自助注册进来的客户 |
| 专属实例(企业版) | 同一份代码,一份专属部署 | 网络与数据库隔离 | 合规、私有网络、要自己的域名与审计 |

两栏是**同一份代码、同一套迁移、同一条租户边界**,差别只在物理摆放。这正是
`deployment_mode` 已经定下的形状([平台架构](platform-architecture.md) §2):
`saas` 档启用登录/注册/工作区/计费;`selfhost` 档是单租户 N=1 且不装计费插件的
同一份代码。**selfhost 是「客户自己想跑一份」的选项,不是「我们不敢开共享」的默认。**

## 2 共享部署要成立,三件事是硬要求

下面三条不是选项,是共享部署的准入条件:任何一条做不到,整盘不成立。

### 2.1 隔离落在库上,不落在每条 SQL 上

应用层过滤的强度是「漏一处就串数据」;行级安全的强度是「漏一处就报错」。共享部署
里数据的价值决定了必须是后者。

策略只有 013 与 018 两版建过,覆盖 14 张表。之后加进来的表都没有,包括工作区与身份
这一层最要紧的几张:工作区在 `memberships` 里、项目级的值在 `project_settings` 里、
邀请在 `invitations` 里、插件启停在 `plugin_tenancy` 里、配额用量在 `quota_usage` 里,
还有 `audit_log`、`agent_sessions`、`user_sessions`。全部清单见
[工作分解](../plan/wbs.md) §6.6。

今天没出跨客户数据,是因为只有一家客户在用,**不是因为隔离成立**。

| 差在哪 | 后果 |
| --- | --- |
| 新表没有策略 | 插件那条受限会话读到的是**所有**客户的成员、邀请、插件启用配置 |
| 核心自己的连接不设 `gwei.tenant` | 核心的一次漏判直接跨客户,策略帮不上 |
| 没有「哪些表必须开策略」的清单 | 新加一张表,没人会想起来给它开策略——这正是上面第一行的成因 |

第三行是前两行的根:**策略靠人记,就等于没有策略**。清单落地形状是「迁移里声明
哪些表必须受策略约束,缺了就是启动失败」,不是一份文档。

### 2.2 一个工作区能在十分钟内自己接完,不改库不找人

今天的注册只做了一半:人注册进来,落在 `registration_tenant` 指定的**那一个**工作区里
(`engine/auth/registration_store.py` 的 `create_user`)。没有「注册即建工作区」这条路
——`POST /api/auth/register/verify` 之后,人属于哪个工作区由配置决定,不由他决定。
建完工作区之后的接入也还是手工步骤。两半都在工作分解 §6.2。

判据:一个陌生人拿到部署地址,自己走完注册 → 建工作区 → 接第一个来源 → 第一条工作流
跑通,全程不碰数据库、不找人要凭据。走不完时,每一步都要说清缺什么。

### 2.3 用量能变成钱,而且对得上账

计费单位没定(§6.3)。共享部署里这一条不落地,产品就只是「免费额度」。
判据:给定一个月的数据,账单条目能逐条对上账本与 LLM 计量;对不上的行要能列出来。

## 3 选专属实例时,共享那一半不白做

专属实例**不换代码**,所以共享 SaaS 里做的隔离、开通、计量它全部继承。区别只有三处:

| 关注点 | 共享 | 专属 |
| --- | --- | --- |
| 工作区个数 | 任意 | 通常一个(把整个部署当自家组织) |
| 注册 | 自助,对外开放 | 通常关掉,由管理员建 |
| 计费插件 | 装 | 按合同装或不装 |

所以「先只卖专属实例」在技术上等价于「`deployment_mode=selfhost` + 手工建租户」,
不需要为它删掉任何东西;但**共享 SaaS 里那些工作必须做完,专属实例才卖得出去**——
一套连客户之间都隔离不干净的代码,装进客户的机房同样不安全。

## 4 和插件的关系

插件是**主体**,不是配置项([目标](goals.md) §形态)。共享部署里这层意思更硬:
同一个插件实例要同时服务多个客户,那么「它被允许在哪几个工作区、哪些仓库上自动做什么」
必须在每次调用时判定,不能靠部署隔离兜底。

- 每一次进出插件的调用都带着租户;插件读库走 `plugin_session`,事务里 `SET LOCAL` 租户
- 插件的能力解析按 (租户, 目标),选不到直接抛,不跨租户回退

未落地的那一半是**插件的数据可见范围**:今天 `v_plugin_changes` 这类视图按租户列收口,
但视图背后的基表授权与策略必须同时成立才有效。这一条与 §2.1 是同一件事。

## 5 结论

| 判断 | 依据 |
| --- | --- |
| 共享部署是默认形态 | SaaS 的定义就是「一个部署卖多家」;租户边界已经在代码里 |
| 专属实例是同一份代码的另一种摆法 | `deployment_mode` 已定:saas / selfhost 唯一代码路径 |
| 隔离必须做到库级 | 共享部署下应用层过滤的失效率不可接受 |
| 自助开通比计费更靠前 | 没有自助开通就不存在 SaaS 这个产品,只是我们替客户开库 |
| 插件在共享部署里必须按调用判租户 | 一个插件实例同时服务多个客户 |
