# 目标

> 状态:现行 | 日期:2026-11-02
> 读者:所有人
> 口径:本文只写目标与由目标推出的硬约束。怎么实现见 [变更单元契约](change-unit-contract.md),边界与取舍见 [平台架构](platform-architecture.md)。

GweiOps 是 AI 驱动的运维智能体平台:把外部信号变成外部世界里已经验证过的改变。名字取自《易经》第 63、64 卦——既济(事已成)、未济(事未成)。

## 形态:全 AI 化的 DevOps

平台与传统 DevOps 工具的差别不是"多了个 AI 助手",是**判断权归谁**:

| 层 | 传统 DevOps | 全 AI 化 |
| --- | --- | --- |
| 执行 | 人写 runbook,工具照办 | 系统执行,人不看细节 |
| 判断 | 人决定改什么、什么时候改 | 系统提出意图,人只判可逆性 |
| 价值 | 人定"值不值得冒这个险" | **这一层永远是人的** |

所以"决策不一样"是这句的意思:前两层交出去,第三层守住。半夜两点该不该重启生产数据库,只有人能答;重启本身该不该自动做,由窗口、验证与履历答。

这个形态反过来约束两件事,都由它直接推出,不是额外选择:

- **插件是主体,不只是配置项。** 插件从接入、诊断、执行到报告贯穿全流程,那么"这个插件被允许在哪些仓库上自动做什么"就是一条授权,与人的授权同一条链。授权清晰 = 可撤可验的地方自动做;授权不到、不可逆的地方才等人。`人在回路,不在闸门` 靠它落地,不是靠人的作息。
- **资源模型必须镜像上游。** 用户输入的世界是 GitHub / CNB 那套(工作区 / 项目 / 仓库),授权按主体 × 资源 × 动作沿链继承。界面像不像是次要的,权限的形状必须像——否则"上游能表达的边界,平台表达不了"。

## 四条目标

1. **半夜不吵醒人。** 信号来自 Issue、监控告警、CVE 源、扫描器;系统在夜间把信号变成已验证的外部改变,人早上只做判断,不负责复原现场。
2. **一个人也敢打。** 几百人才敢运维的系统,几个人甚至一个人就敢打,包括功能更新与金丝雀发布。
3. **只绑定,不自建。** 不实现监控、不实现金丝雀,也不自建 Git 与 CI;把已有的运维基建接进来,高度自动化并保留人在回路。插件可替换,社区能改自己需要的地方。
4. **闭环四段。** 触发 → 诊断修复 → 部署报告 → 学习,或回滚。

## 由目标推出的硬约束

| 约束 | 来自哪条目标 | 怎么判 |
| --- | --- | --- |
| 平台不制造可逆性,只登记并兑现它 | 2、3 | 撤销由下游执行;核心不出现运维动作调用 |
| 人在回路,不在闸门 | 1、2 | 可逆变更先做后报;不可逆变更先报后做 |
| 该不该自动做,由"需不需要人"决定,不由人的作息决定 | 1、2 | 自动收敛的能力(可撤、可验)不设待审;盖不住验证观察期或读不到窗口的一律阻断等人 |
| 平台不假设与下游同机 | 3 | 单元带 binding,提供者声明 binding |
| 能力按 (租户, 目标) 解析 | 3 | 选不到直接抛,不跨目标回退 |

## 不在目标里

自建 Git、CI、监控、金丝雀;通用编程助手;存储指标;替客户写业务代码。
