# 变更单元契约

> 状态:设计待审(2026-11-02) | 读者:架构 / 后端 / 插件作者
> 口径:本文只写合同,不写路线图,不写历史。标注「提案」的内容尚未实现。

## 1. 一句话

平台不制造可逆性,只登记并兑现它。一次运维响应 = 一个**变更单元**;单元的职责是把一个意图落成一次可撤销的外部改变,并给出一次可判定的结论。

两条推论,都是硬约束:

- **核心不实现任何运维动作。** 下游提供能力,平台提供承诺。核心一旦自己实现一次金丝雀,客户用 Argo Rollouts 时就会有两套语义,"随时可对接"当场失效。
- **平台不假设自己与下游同机。** 单元必须带 `binding`,提供者必须声明自己服务哪个 `binding`。两者不一致时拒绝执行,不降级、不猜测。

## 2. 单元的字段

| 字段 | 含义 | 由谁产生 |
| --- | --- | --- |
| `intent` | 触发来源的引用 + 证据(为什么现在要动) | 来源插件 + 判定规则 |
| `binding` | 这次变更作用在哪个下游目标(主机 / 集群 / 租户实例) | 调用方 |
| `incident_id` | 同一次事故里做的变更共用它;空 = 不属于任何一次(人工单发) | 工作流或外部 harness |
| `idempotency_key` | 这次效果的身份;重放时据此复用既有结论,不二次外呼 | 调用方(工作流步骤) |
| `effect.execute` | 一次下游调用:任务名 + 参数 | 效果插件 |
| `effect.undo` | 一次下游调用:任务名 + 从句柄取参数 | 效果插件 |
| `effect.window` | 还能撤回多久;秒数或 `unbounded` | 平台执行前后各读一次 |
| `effect.verify` | 取数 + 判定规则(阈值 + 持续时长) | 验证插件 + 策略 |
| `handle` | 撤销句柄 | 下游返回,平台持久化 |
| `verdict` | 保留 / 回滚 / 阻断等人 | 人或沉默默认 |

`verdict` 有七个结论,每条路径结束时都必须落在其中之一,而且都要落一行账:

- `kept` —— 验证通过,仍在窗口内。
- `rolled_back` —— 已经撤回:验证没过、窗口不足、人工撤销。
- `blocked` —— 没有执行,等人:窗口读不到、盖不住响应时延、放行范围外、读窗口时就报错。
- `vetoed` —— 人明确说不做。
- `failed` —— 确定没动:请求没发出去(构造失败、缺凭据、参数不合法),或下游明确拒绝(4xx)。可以照原样重试。
- `unknown` —— 不知道动没动:请求发出去了,但没拿到结论(超时、连接断、5xx),也就没有句柄。要人去下游核。
- `irreversible` —— 确实动了,而且撤不回来:没句柄、执行后读不到窗口、撤销本身也失败。

`pending` 是刚建好、还没走,不算结论。

下游报错不是"这次没发生",而是一种结论:请求可能已经到了对面。所以 `irreversible` 说的不是"动过了",而是**平台再也无法兑现这个单元的撤销承诺**;具体哪一步、什么错,写在 `reason` 与 `facts.error` 里。

`failed` 与 `unknown` 的分界由提供者给出,不是平台猜的:提供者在 `execute` 里认得出没碰到下游时抛 `EffectNotApplied`,平台记 `failed`;抛别的异常一律记 `unknown`。这条分界值得较真——记成 `failed` 的东西重试一次就安全,记成 `unknown` 的东西重试之前得先去下游看一眼。

一个单元只有一个效果。要改三处就是三个单元,共享同一个 `intent`——撤销的原子性由单元的粒度保证,不由事务保证。

提供者的 `tenant` 为空表示它不按租户隔离(例如一个 GitHub 适配器服务所有租户);解析先找精确租户,再退化到这种共享提供者。`binding` 始终精确匹配。

单元不持有业务表,也不改写 Issue 或 PR;它只记录"我发起过什么、拿回了什么句柄、结论是什么、作用在哪个目标"。

## 3. intent 的形状

intent 是推理提供者(harness 或参考实现)唯一被允许产出的东西:它描述「打算做什么」,不描述「已经做了什么」。

| 字段 | 含义 |
| --- | --- |
| `summary` | 一句话结论 |
| `evidence` | 依据列表,每项 `{kind, ref}` |
| `effects` | 候选效果列表,每项 `{capability, args}`;args 要够一次真实调用 |
| `rationale` | 为什么选它 |

校验在控制面做(`engine/change_unit/intent.py`),不信任提供者:形状不对就是 `blocked`,不重试——重试归提供者,判断归平台。提供者拿不到下游凭据,也拿不到执行结果。

### 3.1 信号

`intent.propose` 的入参是信号,不是原始 webhook:两种来源进来,同一种说法出去。

| 字段 | 含义 |
| --- | --- |
| `source` | `github` / `alertmanager` |
| `subject` | 主体:`owner/repo#3` 或服务名 |
| `title` / `detail` | 出了什么事 |
| `severity` | `critical` / `medium` / `low` |
| `ref` | 来源侧的稳定标识(issue 号 / 告警 fingerprint) |

来源专有的字段随信号一起交出去(`github` 带 `repo` 与 `issue_number`,告警带 `labels` 与 `annotations`),由提供者决定用不用——回评这种效果需要它们,而平台不去理解任何一方的语法。

监控来源可以用 `annotations.gwei_effect` 随告警带一个动作声明(JSON:`{capability, args}`)。参考提供者只做翻译,不替运维决定做什么;没有声明就是空 effects。动作声明指向一个没人提供的能力时,该效果被记成 `blocked`,其余效果照常推进——一个够不着的动作不该让整条链路崩掉。

## 4. 两条路径

| 判定 | 夜间动作 | 人的动作 | 整夜沉默时 |
| --- | --- | --- | --- |
| 可逆,且窗口 ≥ 人的响应时延 | 执行 → 验证 → 入待审 | 早上审:保留或一键回滚 | 保持运行 |
| 不可逆,或窗口读不到 | 阻断,不执行 | 审批后才执行 | 维持阻断 |

没有第三条路径。任何"半自动"实际都落在第二类——它在等人,只是没明说。

### 4.1 阻断不是终点

第二类路径的出口只有两个,都由人触发,都写一行账:

| 动作 | 含义 | 之后 |
| --- | --- | --- |
| 放行 | 人此刻在场,允许执行 | 照常读窗口、照常验证;验证不过照样回滚 |
| 否决 | 人决定不做 | 记为 `vetoed`,不再执行 |

放行不放宽判定口径,只改一个输入:人的响应时延从"睡一觉"变成"现在"。所以执行后的窗口检查问的是"撤得了吗",而不是"到我睡着之前撤得了吗"。真正不可逆的那类,放行并执行之后会被如实记成 `irreversible`——账本不接受一个兑现不了的"可撤"。

## 5. 窗口是读来的,不是声明的

- **两种形态。** 秒数(下游保留旧状态:revision、快照),或 `unbounded`(撤销靠对称操作:把副本数缩回去,目标还在就一直能撤)。两者都没有即 `unknown`。
- **只认秒。** 下游若按次数保留(如 Deployment 的 `revisionHistoryLimit`),由插件换算成保守秒数;换算不了返回 `unknown`。
- **`unknown` 一律当不可逆。** 宁可误判为不可逆,不可误判为可逆。
- **执行前后各读一次。** 执行前读决定走哪条路径,执行后读核实撤销仍然兑现得了;两次不一致以第二次为准,差异记进账本。
- **窗口会过期。** 撤销之前平台按自己的时钟再判一次:过了窗口就拒绝,不把下游已经不再保证的状态重新说成"可撤"。没有句柄、读不到窗口、已经撤销过,同样拒绝。判定在 [engine/change_unit/undo.py](../../engine/change_unit/undo.py),只看句柄、窗口、以及从执行到现在的时长。

只认秒的理由:窗口唯一要与之对标的东西是人的响应时延。次数无法与人比大小——一百次发布会持续两个月,也可能持续二十分钟。

## 6. 平台只允许三个动作

全部与实现无关,因此可以穷举:

1. **换下游** —— 改用窗口够长的绑定(Argo Rollouts 而不是裸 `kubectl set image`)。
2. **换形态** —— 把动作降级成天然可逆的形式:只出 PR、只开 feature flag、只做只读诊断。
3. **阻断** —— 停下等人。

## 7. 插件的义务

1. 每个效果必须提供 `undo`;没有 `undo` 的插件只能出现在第二类路径。
2. 必须返回 `handle`;不返回即视同没有 `undo`——平台无法兑现一个没有句柄的撤销。
3. `verify` 必须是可判定的阈值,不接受"人工看一眼"作为验证。
4. 声明窗口的插件不构成声明;请求"长窗口"不算数,窗口只能被读出来。
5. 提供者必须声明自己服务哪个 `binding`;与单元不一致时拒绝执行。跨环境执行是事故,不是配置错误。
6. 沙箱里的自由与出口上的克制是两件事:agent 在自己的沙箱里可以跑任意命令(修代码、复现、跑测试),但改变外部世界只能经声明了效果的能力。这条靠结构成立——沙箱里没有生产凭据,凭据只在提供者手里。

`undo.kind` 取 `retained` 或 `symmetric`。对称撤销不需要下游保留任何东西,句柄记录的是**执行前**的状态(如原副本数),因此必须在执行前就抓下来。

声明写在清单的 `effects` 块里,由核心在加载期解析并校验:缺 undo、缺窗口读取来源、验证不可判,都在注册时被拒绝。插件只实现执行面,解释权在核心。

```yaml
effects:
  compose.scale:
    label: 调整 compose 服务副本数
    execute: { task: scale, args: [project_dir, service, replicas] }
    undo: { task: undo_scale, kind: symmetric }
    window: { read: project_present }
    verify:
      - { query: running_replicas, expect: ">= {replicas}", for: 10s }
```

## 8. 一人团队的策略

策略即预授权:同一个人可以既定义策略、又在早上审账本,这不构成逐次审批,因此夜间不会断在"没人签字"上。

判定收敛成两个问题,前一个算得出,后一个只能查:

1. **人到能赶回来的时候,还撤得回来吗。** 窗口与响应时延相比。
2. **这个动作以前在这台下游身上留下过什么。** 账本里的履历。

| 参数 | 含义 | 缺省 |
| --- | --- | --- |
| 人的响应时延 | 窗口要盖过的时长 | 8 小时(睡一觉) |
| 无人值守时段 | 一周里人不在的那一段 | 周五 18:00 → 周一 09:00 |
| 夜间放行范围 | 哪几类能力允许走第一类路径 | 空,不按能力限制 |
| 履历门槛 | 见过几次才下结论 | 3 次 |
| 失败率上限 | 失败占比到多少就不再夜间自动做 | 50% |

无人值守时段不是另加一条禁令,它把响应时延从常量换成"到那之后还有多久":周五傍晚那次发布要盖住的不是 8 小时,是到周一早上的六十多个小时。只有 `unbounded` 盖得住——对称撤销正好属于这一类。

沉默默认与升级对象尚未实现:前者要一个到点会触发的调度器,后者要通知通道。在它们存在之前写进策略,只是不会执行的参数。

### 8.1 履历

窗口说明"撤得回来",不说明"撤回来的概率"。同样一段窗口,连续二十次全成和连续三次全回滚不是一回事:前者夜里直接做,后者该有人看一眼。

履历是同一 (租户, 下游, 能力) 的旧结论聚成的一条:动过下游几次、成几次、回滚几次、上次为什么。它只来自账本,因此可复算、可审计,也能被人拿着账本推翻。

分母只算真正动过外部世界的单元。阻断与否决没有碰过下游,把它们算成失败,等于因为"正确地拦住了"而永久怀疑这个能力。

门槛不满就不下结论:两次失败说明不了"这个动作不行",只说明样本太少。够烂之后的方向只有一个——阻断,让人早上看。成本是一个人点一次头,反过来是把一次夜里的自动回滚变成一次白天的翻倍重来。

人在场时履历不生效:它挡的是"机器自己决定",不是"人已经决定"。没有账本时是"不知道",不是"没问题"。

## 9. 不变量

1. 没有 `handle` 的效果不得进入第一类路径。
2. `window` 只能来自读取,不得来自插件声明。
3. 每个单元必须有一条可判定的 `verify`。
4. 核心代码不得出现任何运维动作的直接调用(k8s / 云厂商 / CI SDK)。
5. 任何出口都必须落一行账,包括下游报错;不可逆单元必须显式标注为不可逆,不允许以"待验证"掩盖。
6. 单元必须带 `binding`,且提供者的 `binding` 必须与之一致。
7. 带 `idempotency_key` 的单元必须配账本;账本里已有同键记录时只复用结论,不得再次执行。
8. 判定的证据只能从账本复算,不接受插件或模型的"经验"。

前四条与第六、第八条都可以机检,第五条是审计口径。

## 10. 现状

- 第一个真实单元已跑通:在 GitHub 上发一条评论 → 回读验证 → 删除撤销 → 再验证为空。能力 `comment.create`,提供者是 [GitHub App 适配器](../../plugins/builtin/adapters/github-app/plugin.yaml)。
- 第二个样例:[docker-compose 动作插件](../../plugins/builtin/actions/docker-compose/plugin.yaml)。能力 `compose.scale`,对称撤销,窗口 `unbounded`;真 docker 往返已验证——`test_real_compose_scale_roundtrip` 在守护进程可用时跑完整一圈(扩容 → 读窗口 → 验证 → 缩回),不可用时跳过。
- 推进器:[engine/change_unit](../../engine/change_unit/runner.py) 做预读窗口 → 查履历 → 判定路径 → 执行 → 后读 → 验证 → 保持或回滚。
- 账本有两个后端,同一套异步接口:`db`(默认,业务库 `change_events` 表,按租户可查、并发追加不丢行)与 `file`(单文件 JSONL,只配演示与离线调试)。选哪个由 `CHANGE_LEDGER_BACKEND` 决定。
- `binding` 已进入单元与账本,并由推进器强校验。解析层已实现:`registry.resolve(capability, tenant=, binding=)` 按 (租户, 目标) 精确匹配,选不到直接抛,不回退。
- 幂等已落地:带 `idempotency_key` 的单元重放时只读账本、复用既有结论,不二次外呼;带键却没有账本直接拒绝。
- 推进器可直接吃注册表:`apply(unit, registry)` 按 (租户, 目标) 解析提供者,解析不到直接抛;已解析的 provider 仍可注入(测试与降级路径),但 binding / tenant 不一致会被拒。
- 同一清单可挂多个实例(每租户 / 每目标一个),实例键默认取清单名;SaaS 下按 `<插件>@<租户>/<目标>` 命名。
- 下游报错不是空白:读窗口、执行、读后窗口、验证、撤销五处各自兜住异常,各写一行账并记下阶段与错因,重放时按这一行复用结论、不把效果再做一遍。测试见 [test_change_failure.py](../../tests/test_integration/test_change_failure.py)。
- 履历:[engine/change_unit/record.py](../../engine/change_unit/record.py) 把账本结论按 (租户, 下游, 能力) 聚成一条,策略据此做第二个问题的判定;intent 提供者也拿得到它。测试见 [test_change_record.py](../../tests/test_integration/test_change_record.py)。
- 测试:[test_change_unit.py](../../tests/test_integration/test_change_unit.py),真 docker 的用例在守护进程不可用时跳过。
- 策略与阻断出口:[engine/change_unit/policy.py](../../engine/change_unit/policy.py) 给出响应时延、无人值守时段与放行范围;放行 / 否决由 `POST /api/changes/{id}/approve|veto` 触发,各写一行账。`by` 以控制台令牌为准([engine/api/auth.py](../../engine/api/auth.py)),没配令牌时才采信调用方写的那个。
