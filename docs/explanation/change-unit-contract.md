# 变更单元契约

> 状态:设计待审(2026-11-02) | 读者:架构 / 后端 / 插件作者
> 口径:本文只写合同,不写路线图,不写历史。标注「提案」的内容尚未实现。

## 1. 一句话

平台不制造可逆性,只登记并兑现它。一次运维响应 = 一个**变更单元**;单元的职责是把一个意图落成一次可撤销的外部改变,并给出一次可判定的结论。

两条推论,都是硬约束:

- **核心不实现任何运维动作。** 下游提供能力,平台提供承诺。核心一旦自己实现一次金丝雀,客户用 Argo Rollouts 时就会有两套语义,"随时可对接"当场失效。
- **平台不假设自己与下游同机。** 单元必须带 `binding`,提供者必须声明自己服务哪个 `binding`。两者不一致时拒绝执行,不降级、不猜测。

## 2. 单元的字段

| 字段 | 含义 | 由谁产生 |
| --- | --- | --- |
| `intent` | 触发来源的引用 + 证据(为什么现在要动) | 来源插件 + 判定规则 |
| `binding` | 这次变更作用在哪个下游目标(主机 / 集群 / 租户实例) | 调用方 |
| `incident_id` | 同一次事故里做的变更共用它;空 = 不属于任何一次(人工单发) | 工作流或外部 harness |
| `idempotency_key` | 这次效果的身份;重放时据此复用既有结论,不二次外呼 | 调用方(工作流步骤) |
| `effect.execute` | 一次下游调用:任务名 + 参数 | 效果插件 |
| `effect.undo` | 一次下游调用:任务名 + 从句柄取参数 | 效果插件 |
| `effect.window` | 还能撤回多久:有到期时间 / 凭旧状态存在 / 算不出到期(见第 5 节) | 平台执行前后各读一次 |
| `effect.verify` | 取数 + 判定规则(阈值 + 持续时长) | 验证插件 + 策略 |
| `handle` | 撤销句柄 | 下游返回,平台持久化 |
| `verdict` | 保留 / 回滚 / 阻断等人 | 判定与验证结果,或人的决定;时间不产生结论 |

`verdict` 有七个结论,每条路径结束时都必须落在其中之一,而且都要落一行账:

- `kept` —— 验证通过,仍在窗口内。
- `rolled_back` —— 已经撤回:验证没过、窗口不足、人工撤销。
- `blocked` —— 没有执行,等人:需要人做判断、窗口读不到或盖不住验证观察期、不在自动收敛范围内、读窗口时就报错。
- `vetoed` —— 人明确说不做。
- `failed` —— 确定没动:请求没发出去(构造失败、缺凭据、参数不合法),或下游明确拒绝(4xx)。可以照原样重试。
- `unknown` —— 不知道动没动:请求发出去了,但没拿到结论(超时、连接断、5xx),也就没有句柄。要人去下游核。
- `irreversible` —— 确实动了,而且撤不回来:没句柄、执行后读不到窗口、撤销本身也失败。

`pending` 是刚建好、还没走,不算结论。

下游报错不是"这次没发生",而是一种结论:请求可能已经到了对面。所以 `irreversible` 说的不是"动过了",而是**平台再也无法兑现该单元的撤销承诺**;具体哪一步、什么错,写在 `reason` 与 `facts.error` 里。

`failed` 与 `unknown` 的分界由提供者给出,不是平台猜的:提供者在 `execute` 里认得出没碰到下游时抛 `EffectNotApplied`,平台记 `failed`;抛别的异常一律记 `unknown`。这条分界值得较真——记成 `failed` 的东西重试一次就安全,记成 `unknown` 的东西重试之前得先去下游看一眼。

一个单元只有一个效果。要改三处就是三个单元,共享同一个 `intent`——撤销的原子性由单元的粒度保证,不由事务保证。

提供者的 `tenant` 为空表示它不按租户隔离(例如一个 GitHub 适配器服务所有租户);解析先找精确租户,再退化到这种共享提供者。`binding` 始终精确匹配。

单元不持有业务表,也不改写 Issue 或 PR;它只记录"我发起过什么、拿回了什么句柄、结论是什么、作用在哪个目标"。

## 3. intent 的形状

intent 是推理提供者(harness 或参考实现)唯一被允许产出的东西:它描述「打算做什么」,不描述「已经做了什么」。

| 字段 | 含义 |
| --- | --- |
| `summary` | 一句话结论 |
| `evidence` | 依据列表,每项 `{kind, ref}` |
| `effects` | 候选效果列表,每项 `{capability, args}`;args 要够一次真实调用 |
| `rationale` | 为什么选它 |

单元落账时存的是**整份 intent**,再补三个平台自己的键:`topic`(这次改动属于哪条讨论,见第 9 节)、`workflow`(哪一次执行产出的)与 `skipped`(这次意图里没落成单元的候选,以及为什么——理由只有在建单元之前才定得下来)。摘要之外的 `rationale` 与 `effects` 必须一起留下来:界面上"为什么是这个做法"与"本来还想做什么"直接读它,不从日志里猜。声明式路径也一样写全,不因为它是平台自己兜的意图就少写。

校验在控制面做(`engine/change_unit/intent.py`),不信任提供者:形状不对就是 `blocked`,不重试——重试归提供者,判断归平台。提供者拿不到下游凭据,也拿不到执行结果。

### 3.1 信号

`intent.propose` 的入参是信号,不是原始 webhook:两种来源进来,同一种说法出去。

| 字段 | 含义 |
| --- | --- |
| `source` | 产出这条信号的适配器名(`github`、`alertmanager`、`caddy`……)。核心不列白名单:接一个新系统不该要求改核心,来源名只要求是个合规标识 |
| `subject` | 主体:`owner/repo#3` 或服务名 |
| `title` / `detail` | 出了什么事 |
| `severity` | `critical` / `medium` / `low` |
| `ref` | 来源侧的稳定标识(issue 号 / 告警 fingerprint) |
| `occurrence` | 单次发作的身份(告警的 `startsAt`)。同一个 `ref` 再次出现是另一件事;留空表示来源不区分多次发作,入口按 `ref` 去重 |

来源专有的字段随信号一起交出去(`github` 带 `repo` 与 `issue_number`,告警带 `labels` 与 `annotations`),由提供者决定用不用——回评这种效果需要它们,而平台不去理解任何一方的语法。

监控来源可以用 `annotations.gwei_effect` 随告警带一个动作声明(JSON:`{capability, args}`)。参考提供者只做翻译,不替运维决定做什么;没有声明就是空 effects。动作声明指向一个没人提供的能力时,该效果被记成 `blocked`,其余效果照常推进——一个够不着的动作不该让整条链路崩掉。

## 4. 两类变更,两个问题

判定不是"可逆吗"一个问题,是两个正交的问题:

1. **这次变更需要人做价值判断吗?**发什么、改哪个策略、冒不冒这个险——这些判断只有人能答。
2. **不需要人时,它能不能自己收敛?**有句柄、读得到窗口、有可判定的验证,坏了自己撤回。

| 类别 | 判定 | 谁在回路 | 兜底 |
| --- | --- | --- | --- |
| 自动收敛 | 不需要人做价值判断,且能自己收敛 | 没有人:执行 → 持续验证 → 不好就回滚 | verify |
| 人在回路 | 需要人做价值判断,或撤不回来 | 人,在执行之前 | 人 |

**自动收敛这一类不设"待审"。**重启、备份、安全 bump、随时可拔的接入——做对了继续跑,做错了 verify 会撤,不需要谁早上点一次头。维护期里最该无人化的正是这些动作:技术含量不高、频率很高、坏了自己能退回去。

**人在回路这一类永远先阻断,而且没有超时。**什么都没发生时,晚决定的成本是零;给它加倒计时,只会在人不在的时候替他做一个他还没做的决定。

**执行之后的窗口是给 verify 用的,不是给人用的。**窗口要盖过验证的观察期:观察期内出问题还能撤回来;观察期过了,这次变更就和其它在跑的东西一样,撤销承诺到期。

### 4.1 阻断不是终点

人在回路这一类的出口只有两个,都由人触发,都写一行账:

| 动作 | 含义 | 之后 |
| --- | --- | --- |
| 放行 | 人此刻在场,允许执行 | 照常读窗口、照常验证;验证不过照样回滚 |
| 否决 | 人决定不做 | 记为 `vetoed`,不再执行 |

放行只改一件事:从"等人"变成"人已经在了"。它不放宽判定口径——执行后照样读窗口、照样验证,验证不过照样回滚。真正不可逆的变更,放行并执行之后会被如实记成 `irreversible`:账本不接受一个兑现不了的"可撤"。

### 4.2 执行之后的两层兜底

`kept` 不是终点,后面还有两层:

1. **平台自己的 verify**:观察期内盯着,失败就撤。
2. **外面的监控系统**:变更之后,系统本身仍在被盯着。出事时告警作为信号进来,平台据此找到相关的那次变更,回滚它,或者做一次关联更新。

第二层能成立,前提是**信号能找回变更**:同一 `binding`、最近一段时间内、作用在同一个主体上的单元。找得到就把 `undo` 提成一个新的单元——它照样读窗口、照样判定、照样落账,撤销不是特权路径;找不到就不猜,这条告警走普通的 intent 流程。

这也说明窗口对第二层兜底的意义:只要下游还留着旧状态(窗口没过期),监控发现的问题就还能**撤**;窗口过了,能做的只有"再改一次",那是新的变更,不是撤销。

## 5. 窗口是读来的,不是声明的

窗口只回答一件事:**此刻还撤得回来吗**。答案有三种,不是两种:

| 答案 | 含义 | 例子 |
| --- | --- | --- |
| 有到期时间 | 下游按时间保留旧状态,到点就没了 | 软删除的回收站、快照与 PITR 保留、对象存储的旧版本过期、凭据轮换的双钥重叠期 |
| 凭旧状态存在 | 撤销靠对称操作或"目标还在",不设到期 | 缩回副本数、换回旧镜像、改回开关、删掉评论 |
| 算不出到期 | 旧状态确实还在,但下游按次数或容量淘汰,给不出时间 | `kubectl rollout undo`(受 `revisionHistoryLimit` 限制) |

- **"凭旧状态存在"是常态,不是例外。** 维护期的稳定性动作几乎全是凭旧状态存在:重启、扩容、回滚发布、改配置——它们都没有时间窗口。
- **"算不出到期"不等于不可撤。** 它只说明我们不知道旧状态什么时候被清掉;撤销时照常尝试,由下游回答成功或失败。把它写成不可逆,等于把一次正常的 `kubectl rollout undo` 判死。
- **因此删掉两条旧规则**:不再要求把按次数保留换算成保守秒数(次数淘汰没有对应时刻,换出来的是编的);也不再"只认秒"。
- **执行前后各读一次。** 执行前读决定能不能自动做,执行后读核实撤销仍然兑现得了;两次不一致以第二次为准,差异记进账本。
- **只有"有到期时间"会过期。** 撤销之前平台按自己的时钟再判一次:过了就拒绝,不把下游已经不再保证的状态重新说成"可撤"。没有句柄、已经撤销过,同样拒绝。判定在 [engine/change_unit/undo.py](../../engine/change_unit/undo.py)。

**读不到窗口仍然是不可逆。** 插件没实现窗口读取、或者下游报错——三种答案一条都没有。那是"不知道能不能撤",不是"能撤但不知道多久";宁可误判为不可逆。

## 6. 平台只允许三个动作

全部与实现无关,因此可以穷举:

1. **换下游** —— 改用窗口够长的绑定(Argo Rollouts 而不是裸 `kubectl set image`)。
2. **换形态** —— 把动作降级成天然可逆的形式:只出 PR、只开 feature flag、只做只读诊断。
3. **阻断** —— 停下等人。

## 7. 插件的义务

1. 每个效果必须提供 `undo`;没有 `undo` 的插件只能出现在人在回路的路径。
2. 必须返回 `handle`;不返回即视同没有 `undo`——平台无法兑现一个没有句柄的撤销。
3. `verify` 必须是可判定的阈值,不接受"人工看一眼"作为验证。
4. 声明窗口的插件不构成声明;请求"长窗口"不算数,窗口只能被读出来。
5. 提供者必须声明自己服务哪个 `binding`;与单元不一致时拒绝执行。跨环境执行是事故,不是配置错误。
6. 沙箱里的自由与出口上的克制是两件事:agent 在自己的沙箱里可以跑任意命令(修代码、复现、跑测试),但改变外部世界只能经声明了效果的能力。这个分工靠结构成立——沙箱里没有生产凭据,凭据只在提供者手里。

`undo.kind` 取 `retained` 或 `symmetric`。对称撤销不需要下游保留任何东西,句柄记录的是**执行前**的状态(如原副本数),因此必须在执行前就抓下来。

声明写在清单的 `effects` 块里,由核心在加载期解析并校验:缺 undo、缺窗口读取来源、验证不可判,都在注册时被拒绝。插件只实现执行面,解释权在核心。

```yaml
effects:
  compose.scale:
    label: 调整 compose 服务副本数
    execute: { task: scale, args: [project_dir, service, replicas] }
    undo: { task: undo_scale, kind: symmetric }
    window: { read: project_present }
    verify:
      - { query: running_replicas, expect: ">= {replicas}", for: 10s }
```

## 8. 一人团队的策略

策略即预授权:同一个人可以既定义策略、又在事后看账本,这不构成逐次审批。

判定只剩两个问题:

1. **哪些能力不需要人。**一天里要做的重启、备份、依赖 bump,没必要逐个签字;把它们划进自动收敛的范围,就是这份策略的全部内容。
2. **哪些动作在下游身上出过问题。**账本里的履历,见 8.1。

| 参数 | 含义 | 缺省 |
| --- | --- | --- |
| 自动收敛范围 | 哪几类能力允许不经过人(环境变量 `AUTONOMOUS_CAPABILITIES`,逗号分隔;写 `*` 表示不筛,只给演示与测试) | **空:一律先阻断等人**——要自动,先点名 |
| 履历门槛 | 见过几次才下结论 | 3 次 |
| 失败率上限 | 失败占比到多少就退回"先阻断" | 50% |

**响应时延不是判定输入。**按"人什么时候会醒"来决定做不做,回答的是错的问题:自动收敛的变更本来就不等人,人在不在都一样;人在回路的变更本来就应该等人,多晚决定都不产生额外成本。窗口要盖住的是 verify 的观察期,不是一个人的睡眠。

**沉默不产生结论。**整夜没人管时,可逆的变更保持运行,阻断的保持阻断——两者都是"什么都不做",系统本来就不会替人做决定。

随时间变化的只有一件事:**撤销窗口会过期**。过期之后 `undoable` 从真变假,这是读取时按当下时钟算出来的事实(见[运行时参考](../reference/runtime.md)的变更账本一节),不是一条要落库的结论——更不是一件需要系统去收尾的事。

### 8.1 履历

窗口说明"撤得回来",不说明"撤回来的概率"。同样一段窗口,连续二十次全成和连续三次全回滚不是一回事:前者直接做,后者该退回"先阻断",让人看一眼。

履历是同一 (租户, 下游, 能力) 的旧结论聚成的一条:动过下游几次、成几次、回滚几次、上次为什么。它只来自账本,因此可复算、可审计,也能被人拿着账本推翻。

分母只算真正动过外部世界的单元。阻断与否决没有碰过下游,把它们算成失败,等于因为"正确地拦住了"而永久怀疑该能力。

门槛不满就不下结论:两次失败说明不了"这个动作不行",只说明样本太少。够烂之后的方向只有一个——阻断,让人早上看。成本是一个人点一次头,反过来是把一次夜里的自动回滚变成一次白天的翻倍重来。

人在场时履历不生效:它挡的是"机器自己决定",不是"人已经决定"。没有账本时是"不知道",不是"没问题"。

## 9. 话题与分支

一次讨论是一个**话题**(`owner/repo#number`),话题上的每次改动是一个变更单元。

GitHub 把 PR 的评论也当作 `issue_comment` 发出来——在"评论"这件事上,issue 与 PR 本来就分不开(PR 在 API 里就是一个带上 `pull_request` 字段的 issue)。分得开的是平台这一侧:

- 事故记下它的话题(`incidents.topic`),账本里每个单元记下 `intent.topic`。
- 同一个话题上已经有打开的 PR 时,新的改动**接着该 PR 的分支走**:任务书里直接写出分支名,`pr.open` 复用已存在的 PR、把这次提交追加到该 PR,不再开第二个。
- 分支上的 PR 已经关闭时,`pr.open` 当场拒绝(记 `failed`,什么都还没碰)——把提交推到一条没人看得见的分支上,是比报错更糟的结果。

"接着哪个分支"不是让 agent 猜:账本记着上一次开出来的 PR 与它的分支;评论落在别人开的 PR 上时,平台再问一次下游要 PR 的分支。聚合逻辑在 [threads.py](../../engine/change_unit/threads.py),测试见 [test_threads.py](../../tests/test_integration/test_threads.py)。

## 10. 不变量

1. 没有 `handle` 的效果不得进入自动收敛的路径。
2. `window` 只能来自读取,不得来自插件声明。
3. 每个单元必须有一条可判定的 `verify`。
4. 核心代码不得出现任何运维动作的直接调用(k8s / 云厂商 / CI SDK)。
5. 任何出口都必须落一行账,包括下游报错;不可逆单元必须显式标注为不可逆,不允许以"待验证"掩盖。
6. 单元必须带 `binding`,且提供者的 `binding` 必须与之一致。
7. 带 `idempotency_key` 的单元必须配账本;账本里已有同键记录时只复用结论,不得再次执行。
8. 判定的证据只能从账本复算,不接受插件或模型的"经验"。

前四条与第六、第八条都可以机检,第五条是审计口径。

## 11. 现状

- 第一个真实单元已跑通:在 GitHub 上发一条评论 → 回读验证 → 删除撤销 → 再验证为空。能力 `comment.create`,提供者是 [GitHub App 适配器](../../plugins/builtin/adapters/github-app/plugin.yaml)。
- 第二个样例:[docker-compose 动作插件](../../plugins/builtin/actions/docker-compose/plugin.yaml)。能力 `compose.scale`,对称撤销,窗口 `unbounded`;真 docker 往返已验证——`test_real_compose_scale_roundtrip` 在守护进程可用时跑完整一圈(扩容 → 读窗口 → 验证 → 缩回),不可用时跳过。
- 发布也是同一个插件里的效果:`compose.release` 把服务切到指定镜像,句柄记下切换前的镜像,撤销就是部署回去,窗口 `unbounded`。触发在 [release_workflow](../../engine/workflows/release.py):PR 合并是人的审核,平台只接合并事件,发布参数(`RELEASE_PROJECT_DIR` / `RELEASE_SERVICE` / `RELEASE_IMAGE_TEMPLATE`)缺一就不发。真 docker 往返见 `test_real_compose_release_roundtrip`,不可用时跳过。
- 推进器:[engine/change_unit](../../engine/change_unit/runner.py) 做预读窗口 → 查履历 → 判定路径 → 执行 → 后读 → 验证 → 保持或回滚。
- 账本有两个后端,同一套异步接口:`db`(默认,业务库 `change_events` 表,按租户可查、并发追加不丢行)与 `file`(单文件 JSONL,只配演示与离线调试)。选哪个由 `CHANGE_LEDGER_BACKEND` 决定。
- `binding` 已进入单元与账本,并由推进器强校验。解析层已实现:`registry.resolve(capability, tenant=, binding=)` 按 (租户, 目标) 精确匹配,选不到直接抛,不回退。
- 幂等已落地:带 `idempotency_key` 的单元重放时只读账本、复用既有结论,不二次外呼;带键却没有账本直接拒绝。
- 推进器可直接吃注册表:`apply(unit, registry)` 按 (租户, 目标) 解析提供者,解析不到直接抛;已解析的 provider 仍可注入(测试与降级路径),但 binding / tenant 不一致会被拒。
- 同一清单可挂多个实例(每租户 / 每目标一个),实例键默认取清单名;SaaS 下按 `<插件>@<租户>/<目标>` 命名。
- 下游报错不是空白:读窗口、执行、读后窗口、验证、撤销五处各自兜住异常,各写一行账并记下阶段与错因,重放时只复用该行账的结论、不把效果再做一遍。测试见 [test_change_failure.py](../../tests/test_integration/test_change_failure.py)。
- 履历:[engine/change_unit/record.py](../../engine/change_unit/record.py) 把账本结论按 (租户, 下游, 能力) 聚成一条,策略据此做第二个问题的判定;intent 提供者也拿得到它。测试见 [test_change_record.py](../../tests/test_integration/test_change_record.py)。
- 测试:[test_change_unit.py](../../tests/test_integration/test_change_unit.py),真 docker 的用例在守护进程不可用时跳过。
- 策略与阻断出口:[engine/change_unit/policy.py](../../engine/change_unit/policy.py) 目前仍按"窗口 vs 人的响应时延"判定,属于第 4 节之前的旧口径,改动记在[工作分解](../plan/wbs.md) 1.3;放行 / 否决由 `POST /api/changes/{id}/approve|veto` 触发,各写一行账。`by` 以控制台令牌为准([engine/api/auth.py](../../engine/api/auth.py)),没配令牌时才采信调用方自报的 `by`。
- `plugins/builtin/actions/k8s-scaler/` 只有空的 `__init__.py`,尚无清单与实现。
