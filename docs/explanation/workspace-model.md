# 工作区模型

> 状态:现行 | 日期:2026-11-16 | 读者:前端、后端
> 上游:[目标](goals.md)、[议题工作台](issue-workspace.md)
> 下游:[身份与授权](identity-and-authorization.md)

界面原来假设只有一个仓库。管三个仓库时,议题板是一张全量表,仓库页是一张全量卡片墙,配置与密钥只有一份 —— 要单独看某个仓库,没有地方点。

工作区这一层已经落下来,侧边栏最上面是选择器,仓库的身份换成"来源 + 仓库全名",上面补回了项目这一级。这份文档写它的判断与边界;人、凭据与成员关系怎么分开,见[身份与授权](identity-and-authorization.md)。

## 1 一句话

**工作区就是租户;它是每一条账的边界,不是一个筛选器。**

## 2 层

```text
工作区(租户) ──项目──▶ 仓库 ──议题 / 变更账本 / 事故 / 执行会话
```

| 层 | 是什么 | 落在哪 |
| --- | --- | --- |
| 工作区 | 所有数据的边界:议题、账本、配置、密钥、成员、配额都在它里面 | `tenants` |
| 项目 | 一组仓库,也是范围闸的中间那一档 | `projects` 里 `parent_id` 为空的行 |
| 仓库 | 一份代码,来源可以不同(GitHub / CNB / GitLab) | `projects` 里 `parent_id` 指向某个项目的行 |

**项目不新开一张表。** `projects` 自引用一次就够:空 `parent_id` 是项目,指向它的行是仓库。同一种东西两个名字和"工作区再开一张表"是同一个错误。

### 2.1 仓库的 name

仓库的身份是 **(租户, slug)**,slug 写 `来源-仓库全名`,`/` 也压成 `-`:

```text
github-acme-api     github 上的 acme/api
cnb-acme-api        同一个名字,另一份代码
acme                项目这一行,没有来源
```

- 分隔符只有一个(`-`),因为它要塞进查询串(`/issues?repo=github-acme-api`),`:` 要转义成 `%3A`
- **slug 不可逆**:`github-acme-api` 拆不回"来源 github + 全名 acme/api"。要这两个值读库里 `source` / `name` 两栏,不从 slug 猜
- 投递里没明说项目时按仓库全名第一段建或取一个(幂等):`acme/api` 的父是 `acme`。要塞进别处改 `parent_id`,这里不猜第二次

## 3 为什么工作区不是新表

队列已经按租户分区;账本、事故、密钥、成员、配额、配置 scope 都带着 `tenant_id`;`tenant_scope()` 已经按它判越权。再加一张叫"工作区"的表,同一个边界有两个名字,还会引出"工作区里的租户"这种没人答得上来的问题。

界面上叫工作区,是因为 `tenant` 是给实现看的词,不是给用户看的词。

## 4 配置属于哪一层

| 配置 | 属于 |
| --- | --- |
| 来源接入、密钥、成员角色 | 工作区 |
| 发布参数(mode / 镜像模板 / 分支) | 仓库,工作区给默认值,项目可以再给一层。已是五层合并:出厂 → 环境 → 租户默认 → 项目默认 → 仓库行 |
| 项目级可见性 / 默认动作 / 凭据 | 项目这一行(`project_settings`),见 §6.4 |

别的 scope 这次没有提升到仓库级:**每个 scope 都要回答"仓库级的值从哪读、回显谁看得见、推给插件时按哪个仓库推"**,这是一圈不小的机制。有第二个仓库需要不同的值再逐项做,一次一个。

## 5 侧边栏

```text
┌ Acme · 4 个仓库 · github/cnb ┐   ← 换它 = 换一整套议题、账本、配置、成员
  搜索  Ctrl K
────── 工作区 ──────
  议题            等我 3
  变更账本
────── 接入 ──────
  仓库  信号源  插件  MCP 接入
────── 工作区管理 ──────
  指标观测  成员  设置
```

- **选择器常驻在导航之上**,不藏进下拉筛选。它换的不是"看哪个列表",是数据边界
- **切工作区回 `/issues`**:停在原页面等于看一个不属于这个工作区的列表
- **导航表不随工作区变长变短**。权限不够看到的应该是"你没有这个工作区的这个权限",而不是功能凭空消失
- **仓库是导航里的一个页面,不是分组**。仓库数量是数据,数据不该决定导航结构
- 徽标只有「等我」一个,数字是当前工作区的;选择器上那个合计是唯一不属于某个工作区的数

## 6 范围与权限

### 6.1 范围闸:一个筛选器、三档

```text
范围  [ Acme · 3 个仓库 ▾ ]  [ 全部仓库 ▾ ]  清空
```

整个工作区 → 某个项目 → 某个仓库,是**同一个筛选器上的三个位置**,不是三段导航。板子只有一个。

- 档记在查询串,不记 cookie:范围是"我现在在看什么",刷新、分享、从详情页点回来都该保持;工作区才是数据边界,那才是 cookie 的事
- **筛在后端收**。两边各写一套"这一行算不算在范围内",迟早对不上
- 侧边栏没有项目分组;项目在仓库页上是分组标题

### 6.2 按范围授权:项目与仓库两档

权限可以带范围,范围是 `projects` 里的 slug,项目与仓库共用一个名字空间:

```text
changes.approve@acme                 整个项目,含以后新增的仓库
changes.approve@github-acme-api      只在这一个仓库上
```

| 判据 | 为什么 |
| --- | --- |
| 只有读账 / 执行 / 放行 / 撤销能收窄 | 它们最终都落在一个仓库上。管人、管密钥、改配置是工作区级的事 —— 一个仓库没有自己的用户表 |
| 带范围的授权不算工作区级权限 | 不点名范围的判定 403,说的是"这个权限只对具体范围生效" |
| 子用户与父按范围逐个取交集 | 父只管 `acme/api`,子用户借角色铺到 `acme/web` 不算数 |
| 项目档覆盖**以后新增的**仓库 | 所以判定链是 repo → project → 工作区,且这一档只能在判定时问 —— 建身份时展开成一份仓库清单,新仓库进来时会漏掉它 |

形状与判据见[身份与授权](identity-and-authorization.md) §4,本文不重复。

### 6.3 一人多工作区

同一个人被邀进第二个工作区时,多出来的是**一条成员关系**,不是第二条密码:`persons` 一条、`memberships` 两条,改一次密码两处同时生效。形状与迁移见[身份与授权](identity-and-authorization.md) §5。

### 6.4 项目级的值

项目是资源,不是标签:它下面几个仓库共享一套发布策略与插件目标。这些值原来只能落在**工作区默认**上(于是"这个项目怎么发布"和"别个项目怎么发布"只能配一处),或者落在每个仓库行上(于是同一个项目的三个仓库抄三份,改一次要改三处 —— 而那些副本迟早有一份没跟上)。

所以项目这一级有自己的一行 `project_settings`,三样东西一个形状:

| 值 | 存在哪 | 谁读 |
| --- | --- | --- |
| 可见性 `workspace` / `restricted` | 库里那一行 | 仓库与项目列表 |
| 默认发布参数 | 那一行的 `defaults` | 发布解析的项目那一层 |
| 项目级凭据 | 值进密钥仓库(`scope=project:<slug>`),那一行只记键与说明 | 配置页;插件按 scope 读 |

| 判据 | 为什么 |
| --- | --- |
| 没有那一行 = 全用工作区默认 | 不写空行占位:空行会让"这个项目配过没有"变成两个答案 |
| 项目默认只在它自己的仓库上生效 | 合并顺序里它在租户默认之后、仓库行之前 |
| 仓库行仍然压过项目默认 | 一个仓库要例外的仍然能例外,不必为了这一条去改项目 |
| 可见性不替代权限判定 | 它只回答"列不列出来"。工作区成员之间照样按角色判 —— 一个项目标了 `restricted`,同一个工作区里的人还是看得见 |
| 凭据的值不进业务库 | 表在业务库里,谁读到库就都读到了;"设了没有"从密钥仓库回答 |
| 发布解析读的是快照 | 解析是同步的(工作流步骤里到处在调),快照由接口写完与启动流程各刷一次,库仍是权威 |

## 7 已有接口

| 接口 | 用途 |
| --- | --- |
| `GET /api/workspaces` | 我进得去的工作区,以及每个里面有几个仓库、来自哪些平台 |
| `GET /api/workspaces/{slug}/repos` | 这个工作区里的仓库,每行带来源、slug 与所属项目 |
| `GET /api/workspaces/{slug}/board?project=&repo=` | 议题板,`project` / `repo` 是范围闸 |
| `GET /api/me` | 我是谁、属于哪些工作区、每个里面是什么角色 |
| `GET /api/workspaces/{slug}/projects/{slug}/settings` | 一个项目的可见性、默认发布参数、项目级凭据(只回答"设了没有") |

工作区**在路径里**:接口是 `/api/workspaces/{slug}/…`,界面是 `/workspaces/{slug}/issues`。理由在[身份与授权](identity-and-authorization.md) §2 第 4 条 —— 资源要有 URL,链接自带"这是哪一道账",刷新、分享、同事点开都落在同一道上。cookie 只说明"上次看的是哪个",它不该能改数据。

一个只属于一个工作区的人不必每条链接都带那一段:没有工作区段时按他最早的那条成员关系回答。界面首屏也这样打开,随后把地址换成带那一段的。
