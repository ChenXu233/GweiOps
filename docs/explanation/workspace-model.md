# 工作区模型

> 状态:现行 | 日期:2026-11-19 | 读者:前端、后端、产品
> 上游:[目标](goals.md)、[平台架构](platform-architecture.md)、[议题工作台](issue-workspace.md)

界面原来假设只有一个仓库:议题板是一张全量的表,仓库页是一张全量的卡片墙,配置
与密钥只有一份。一个人管三个仓库时,这张表里既有 api-gateway 的议题,也有
frontend 的;要单独看某个仓库的议题、某个仓库的发布配置,没有地方可以点。

这份文档定下**工作区**这一层,以及它在界面上、数据上、权限上各是什么。它不改
[议题工作台](issue-workspace.md) 的心智模型——议题仍然是用户唯一要处理的对象,
一条议题仍然是一条时间线;改的是那张表**属于谁**。

## 1 一句话

**工作区是一道账的边界;项目是边界里的一个资源;仓库是项目下的一个对象;议题是
仓库里的一行。**

## 2 有哪些层,哪些不是新概念

| 层 | 是什么 | 谁在用 | 状态 |
| --- | --- | --- | --- |
| 工作区 | 一个团队的边界:议题、账本、配置、密钥、成员都在它里面 | 每个页面都在它之内 | 已有,叫 `tenants` |
| 项目 | 一组仓库所属的资源:`acme` 下可以有 `api` 与 `web` | 范围闸的中间档、项目级配置与凭据的落点 | 已有,是 `projects` 里 `parent_id` 为空的那一行 |
| 仓库 | 一个平台上的一份代码:`acme/api`、`cnb:acme/api` | 议题板的范围、仓库页、发布管道 | 已有,叫 `projects` |
| 议题 | 一个仓库里的一条讨论 | 议题板、议题详情 | 已有,叫 `issues` |

**工作区不是新表。** 它就是租户:DBOS 队列已经按它分区,账本、事故、密钥、
成员、配置 scope 都已经带着它,`tenant_scope()` 已经按它判越权。再加一张
"工作区"表会让同一个边界有两个名字,并引出"工作区里的租户"这种没人能回答的问题。

界面上叫工作区,是因为 **tenant 是给实现看的词,不是给用户看的词**。两个词指
同一行数据。

**项目与仓库是同一张表的两层。** `projects` 自引用一次:`parent_id` 为空的那一行
是项目,指向它的那些行是仓库。为什么不新开一张 `projects` 表——工作区与租户已经
是同一件事,再加一张表会让同一个边界(或同一种东西)有两个名字。为什么不多加一
层"项目"而不是复用——那才是真正的重复,见 §3 的身份表。

项目是**资源**,不只是标签:它有自己的唯一键(slug)、自己的可见性、默认动作与
凭据的位置。少了这一级,`acme/api` 与 `other/api` 只能靠工作区区分,项目的东西
就全堆在工作区级。

## 3 身份:谁是谁

| 对象 | 身份 | 为什么不是别的 |
| --- | --- | --- |
| 工作区 | `tenants.slug` | 已经唯一、已经进队列分区键、已经在令牌里声明 |
| 项目 | (租户, `projects.slug`) | 项目名在租户内唯一就够了;它不需要来源——项目不属于哪个平台 |
| 仓库 | (租户, `projects.slug`),slug 是 `来源:仓库全名` | 平台侧数字 id 只在**同一个来源**里可比:GitHub 的 `12345` 和 CNB 的 `12345` 不是同一份代码,而且有的来源根本不给 id |
| 议题 | (仓库, 平台侧 issue id) 或 (仓库, 议题号) | 议题号在仓库内唯一,且每个来源都有;id 只在同来源内可比 |

唯一键从 (租户, 来源, 仓库全名) 收成 (租户, slug):`slug` 直接把"哪个来源"
写进名字,两种唯一合成一种。

**`-` 留给层级,`:` 留给来源。** 仓库的 slug 是 `github:acme/api`;如果以后要
给子仓做层级,写法会是 `acme-platform/team-a`。两套字符集不重叠,所以"来源叫
`acme`、仓库叫 `api`"写出来的 `acme:api` 与"github 上的 `acme/api`"写出来的
`github:acme/api` 永远是两行。

`projects.source` 记"这个仓库来自哪个平台",它与"哪个团队"是两个正交的维度;
项目行的这一栏是空串——项目不属于任何平台。`github_id` 是"来源自己给的 id,
可以没有",不再是身份。

**默认归属:`acme/api` 的父是 `acme`。** 投递里没有明说项目时,按仓库全名的
第一段建或取一个项目。这只是没有更好信息时的默认值:要塞进别的项目,改
`parent_id` 就行,这里不猜第二次。

## 4 界面:侧边栏怎么放

侧边栏从上到下四段,工作区在最上面,因为它决定的不是"看哪个列表",而是
"这里的每一行数据来自哪道账"。

```text
┌ 工作区选择器 ──────────┐   ← 换它 = 换一整套议题、账本、配置、成员
│  Acme  · 4 个仓库 · github/cnb │
└────────────────────────┘
  搜索  Ctrl K
────────── 工作区 ──────────
  议题            等我 3
  变更账本
────────── 接入 ───────────
  仓库
  信号源
  插件
  MCP 接入
────────── 工作区管理 ──────
  指标观测
  成员
  设置
──────────
  外观 / 当前身份
```

规则:

1. **选择器在导航之上、常驻**,不藏进下拉筛选。它不是"筛一下",它换的是数据边界。
2. **切工作区回默认页**(`/issues`)。停在原页面等于看一个不属于这个工作区的列表,
   而那正是"全都糅在一起"的重演。
3. **导航表只有一张**。各组不随工作区增减——权限不够看到某页时,页在那里、内容
   说的是"你没有这个工作区的这个权限",而不是导航自己变短(导航变短会让人以为
   功能没了)。
4. **仓库是导航里的一个页面,不是导航的分组**。仓库一多,把它们做成可展开的树会
   让侧边栏长度随数据增长;分组交给议题板与仓库页自己做。
5. **徽标只有一个**,仍然是"等我"的条数,数字是当前工作区的;选择器上另有一个
   跨工作区的合计,那是唯一一个不属于某个工作区的数。
6. **项目与仓库都进一个筛选器,不进导航。** 见 §5 的范围闸。

选中项记在 cookie(`gwei-workspace`)里,不是 localStorage:服务端渲染时也要
知道它在哪个工作区,否则首屏画的内容和挂载后换掉的对不上。

## 5 页面:在仓库之内还是在外

每个页面回答一个问题,工作区这一层只改变它看到的数据范围,不改变它问什么。

| 页面 | 问什么 | 范围 |
| --- | --- | --- |
| `/issues` | 要我做什么 | 当前工作区的全部仓库 |
| `/issues/{id}` | 这条怎么走到今天 | 那一条议题 |
| `/changes` | 改过什么、还能不能撤 | 当前工作区的账本 |
| `/repos` | 这里有哪些仓库、各自什么状态 | 当前工作区的仓库,按项目分组 |
| `/repos/{id}` | 这一份代码怎么发、它属于谁 | 那一个仓库 |
| `/signals` | 信号从哪进来 | 当前工作区的来源适配器 |
| `/marketplace` `/mcp` `/team` `/settings` | 谁能做什么、配了什么 | 当前工作区 |

**范围闸:一个筛选器、三档。** 整个工作区 → 某个项目 → 某个仓库,是同一个筛选器
上的三个位置,不是三段导航。

```text
范围  [ Acme · 3 个仓库 ▾ ]  [ 全部仓库 ▾ ]  清空
```

- 档记在查询串里(`/issues?project=acme`、`/issues?repo=github:acme/api`),不记
  cookie:范围是"我现在在看什么",刷新、分享、从详情页点回来都该保持;工作区才是
  数据边界,那是 cookie 的事。
- **筛在后端收。** 前端只把档传上去,不自己过滤一份——两边各写一套"这一行算不算
  在范围内",迟早对不上。
- 选了仓库时项目档跟着它显示,换项目则清掉仓库档:上一档的仓库不一定属于它。

为什么不给每个仓库做成侧边栏里可展开的分组:仓库数量是数据,导航长度会被数据拉长,
而且真正的问题始终是"我现在要做什么"。项目在仓库页上是**分组标题**,不是导航项。

**仓库页(`/repos/{id}`)是"仓库作为目的地"唯一成立的地方**,而且只从一个仓库卡片点
进去:身份、发布管道、它属于哪个项目。发布管道放这里而不是全塞设置页——设置页那份是
"工作区默认 + 所有仓库行"的总表,管的是给整个工作区定调子;仓库页管的是这一份代码自己
怎么发。两处读写同一份数据,保存完就原地重取,不留第二份状态。

## 6 配置:哪些属于工作区,哪些属于仓库

| 配置 | 属于谁 | 现状 |
| --- | --- | --- |
| 来源接入(哪个 GitHub App、哪个 CNB 令牌) | 工作区 | 已在 `plugin_settings` scope(租户级的公共值 + 覆盖) |
| 发布管道 | **仓库**,工作区给默认值 | 设置页配工作区默认与总表,仓库页(`/repos/{id}`)配这一仓的覆盖 |
| 密钥(MCP 出口) | 工作区 | 已在 `api_keys`,带 `bindings` 收窄到具体下游目标 |
| 成员与角色 | 工作区 | 已在 `users` / `roles`(RBAC 是租户内的概念) |

发布配置已经是"工作区默认 + 仓库覆盖"的形状,别的配置**不急着"提升"到仓库级**:
每个 scope 都要回答"仓库级的值从哪读、回显谁看得见、推给插件时按哪个仓库推",
这是一圈不小的机制。等真有第二个仓库需要不同的值再逐项做,一次一个 scope。

## 7 权限:人在工作区里是什么

| 情况 | 今天是什么 | 结论 |
| --- | --- | --- |
| 一个团队多个仓库 | 一个租户多个 `projects`,可分成多个项目 | 已支持:仓库页按项目分组,范围闸能收窄到项目或仓库 |
| 一个人属于多个团队 | 每租户一套 `users` 行 | **不连续**:同一个人在两个工作区里是两条用户记录 |
| 一个团队里按仓库分工 | RBAC 只有租户级权限 | **不支持**:不能让某个人只管 `acme/api` |

第二、三行是这一层真正的缺口,也是 SaaS 的关键:**没有它们,工作区只是把列表
分组,不是"每个项目自己的用户权限"。**

接口形状先定下来,免得以后把工作区换成新表:

- `GET /api/workspaces` 返回当前令牌看得见的工作区。令牌声明了租户时只返回它
  自己那一个——看得见再把其余的藏起来,只会让人点到一个"它在这儿但不能看"的
  空白页。
- 切换工作区**不换令牌,换的是请求里的租户**:沿用 `tenant_scope()` 已有的
  规则(令牌声明的租户优先,两者不一致是 403,不是悄悄覆盖)。服务端不改一张
  表就换一道账,这是租户原语带来的现成好处。
- 按仓库分工给 RBAC 加一个维度:权限判定的入参从 `(actor, permission)` 变成
  `(actor, permission, scope)`,scope 是一个仓库或空(空 = 整个工作区)。现有
  租户级角色等价于 scope 为空,行为不变。

## 8 不做的事

- **不新增"工作区"表或"项目"表**:前者与租户重复,后者就是 `projects` 里 `parent_id`
  为空的那一行——另开一张表等于给同一种东西起第二个名字。
- **不做跨工作区看板**:跨工作区的合计只有侧边栏那一个数。一道账里发生的事不该
  和另一道账里的事并排出现在同一张板上——那会让人分不清哪个决定作用在哪。
- **不把仓库做成导航分组**:仓库数量是数据,数据不该决定导航结构。
- **不在这次重写配置 scope 的仓库级能力**:见 §6。

## 9 落到代码上的入口

| 租户上下文与越权判定 | `engine/api/auth.py` 的 `tenant_scope` |

| 当前工作区(前端) | `frontend/packages/core/composables/useWorkspaces.ts` |
